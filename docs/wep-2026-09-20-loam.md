# WEP: Loam — Lowered Operators, Ahead-of-time Modules

## Context

Wado has no tensor story. The closest thing in the tree is
`example/microgpt.wado`, a scalar autograd graph where every arithmetic
operation allocates a `Value` node. It is a faithful port and a useful GC
benchmark. It is not a foundation for machine learning work.

What Loam is for is inference on the device: a browser or a phone, on WebGPU.
Those places share two constraints that a datacenter never has. Every byte of
the module is downloaded before the first token, so the module must carry only
what the model uses. And the process starts cold, so there is no warmup to
amortize a JIT against. An engine that ships an interpreter and the graph as
data pays both; a module compiled from the graph ahead of time pays neither,
and that is the shape Loam takes.

Four findings from the 2026 literature drive this proposal.
`docs/research-ml-inference-webgpu.md` records the survey they come from.

Compile-time shape checking has become implementable. Dependent and refinement
types both demand proofs to decide type equality, which is why neither was
adopted in practice. Staging replaces the proofs with assertions evaluated as
compile-time computations, and the ECOOP 2026 work validated it on ported
ocaml-torch programs.

Axis notation has converged on einx, whose bracket marks the axes an operation
actually sees. Static checking of it exists only as external stubs, because
Python cannot say in a type what an operation does to a shape. That is a
constraint of the host language rather than of the idea, and it is the reason
this design has no notation layer at all.

Quantization formats are a moving target parameterized by block size, scale
representation, and rotation, not a fixed list of names.

Fusion's objective function is not what it was. On WebGPU at batch size 1,
dispatch count dominates and kernel quality does not. That objective belongs to
the GPU work, and naming it here is what bounds the claims a CPU MVP can make.

Gale is the architectural precedent: a static compiled fast path with
escalation to a runtime tier. This WEP adopts five properties of it:

- The escalation boundary is a decidability result. Gale escalates because the
  lookahead language of a recursive ambiguous prefix is non-regular, so subset
  construction provably does not converge.
- The escalation sites are enumerable and named. Each site Gale's
  simulator decides is pinned by a fixture and visible through `gale dump --atn`.
- Cost routes as much as correctness does. Sites that belong on the simulator
  for correctness stay static where measurement showed the simulator too slow,
  and the divergence is pinned rather than hidden.
- An unused mechanism costs nothing. A grammar needing no simulator carries
  none and is byte-for-byte unaffected.
- The runtime is inlined into the generated file, which is what removes
  version drift between generator and runtime.

Version drift is a problem the field has not solved. ONNX opset drift and
checkpoint incompatibility are both drift between a model artifact and the code
that runs it, which is what the last property removes.

Kiln makes the staging available without a language change. Wado has neither
const generics nor general compile-time evaluation, so an extent cannot be
carried as an integer in type position. A Kiln generator, however, runs
arbitrary Wado at compile time and emits Wado source, which is staging. Gale
already works this way. Loam is therefore a package, not a language feature.

## Decision

### Name

**Loam** — Lowered Operators, Ahead-of-time Modules.

A model that submits to fixed shapes at build time gets fused kernels, and gets
its shape errors at build time instead of wrong numbers at run time. The
constraint is the mechanism, not a limit on it.

Loam is the earth a foundry mould is made of, and a mould holds its shape
before any metal is poured. Kiln fires such a mould, and Loam is a Kiln
generator. The name is a short natural noun, as Gale, Kiln, Jade, and Marl are.

### A Kiln Generator, Not a Library

Loam is invoked as a Kiln generator over a model graph and its checkpoint:

```wado
use { Weights, forward } from "./model.onnxtext" with {
    generator: {
        module: "wado-lang:loam@0.1",
        inputs: ["./model.safetensors"],
    },
};
```

A library would place shape checking at run time, where every other framework
already has it. Only a generator can place it early enough for a shape mismatch
to stop the build.

The graph is what the generator reads today. Roadmap step 5 adds the checkpoint
named in `inputs`, and the check of its header against the graph.

Three properties follow from the choice, and each answers a standing problem in
the field:

- A Kiln generator runs in a full Wasm sandbox. A build-time code generator that
  reads untrusted model files is an obvious attack surface, and both `build.rs`
  and `setup.py` execute with the developer's privileges. Loam cannot.
- The generated module carries its own kernel runtime, inlined as Gale's is.
  There is no separate runtime package to version-match, so opset drift has no
  place to occur.
- The generated module is ordinary Wado. It is readable, debuggable, and
  optimized by the same pipeline as any other Wado source.

Loam reads its graph with a Gale-built parser, so its own source imports a
module Kiln produces. The reader names `../grammar/Onnx.g4` at its use site, and
Kiln builds the parser when it builds the generator. Kiln's WEP covers that
under §"A generator may use a generator".

### The Graph Is ONNX

A forward pass is read rather than written. Loam takes a model graph in a
language the field already has, and the first one is ONNX, with StableHLO to
follow as a second front end.

The operators mean what ONNX says they mean: broadcasting, each operator's
definition, and the opset version that fixes it. Loam declares the opset range
it reads and reinvents none of it. This is where most of the robustness comes
from. A graph language of Loam's own would have had semantics of Loam's own, and
every rule of them would have been Loam's to specify, to test, and to get wrong.
ONNX's rules come with a reference implementation and a conformance suite, and
that suite is the oracle the kernels are tested against.

A graph arrives in either of ONNX's two forms, and the generator picks by
extension. `.onnx` is the protobuf form, which is what an exporter writes and
what the backend test data ships; `package-loam/src/onnx_proto.wado` reads it
over `core:protobuf`. `.onnxtext` is the textual format `onnx.parser` reads and
`onnx.printer` writes, named as onnx-mlir names it, and a Gale grammar parses
it.

Both produce the `Graph` in `package-loam/src/graph.wado`, so nothing after the
reader knows which form it came from. A fixture written here takes the text
form, since a textual graph is a few kilobytes and shows a diff, as
`package-loam/example/mlp.onnxtext` does. The `.onnx` files under
`package-loam/tests/onnx/` are committed too, and they are copies of ONNX's own
test data rather than anything edited here. The two are not equivalent
encodings. Protobuf is ONNX's canonical form, so
where they disagree it is the one that wins.

An inline value in the text form is read as `onnx.parser` reads it, into the
protobuf field it would fill. A `float16` or `bfloat16` element is therefore an
integer, the bit pattern `int32_data` holds, and `15360` is `1.0`. A float may
end at its point (`1.`) but not start there (`.5`).

The graph names its weights, and either the graph or a checkpoint supplies
them. A `.onnx` may carry its initializers' data itself, and that is enough to
run. Otherwise an initializer's name is the key into the checkpoint, so the
graph is the `from` literal and the checkpoint an `inputs` entry, and a sharded
checkpoint is several entries.

An ONNX shape is positional, with a `dim_param` where a dimension is symbolic.
That is the extent half of an axis and none of the identity half, so the axis
schema of the next section names the axes of the graph's inputs and
initializers, and the shape algebra carries those names and extents through
every operator by its ONNX signature. An intermediate value is never named by
hand. A `dim_param` is a symbolic extent; a `dim_value` is a static one.

A graph also declares the shapes of its own outputs, and those are merged
against what the nodes produced on ONNX's terms (`mergeInDimensionInfo`): two
static extents that differ are the conflict, while a `dim_param` names the axis
in the author's words and a `?` names nothing, so neither can disagree with the
schema's own axis name. A rank that differs is a conflict.

This settles who Loam is for. A graph reaching it has already run once, in the
framework that exported it, so its shapes are consistent by construction. What
the build catches is the seam that framework never saw: a checkpoint whose
extents disagree with the graph, and a caller whose tensors disagree with the
boundary.

### The Graph Is the Schema, the Checkpoint Is Data

The graph is the schema, and the generated code is a function of it. A
checkpoint carries data, behind a header of its own: a safetensors header is a
length-prefixed JSON blob at the front of the file carrying tensor names,
positional shapes, dtypes, and offsets. The build checks that header against the
graph and reads nothing further down the file.

Kiln's probe is what makes that pay. A generator reports how many leading bytes
determine its output, and the build keys on that range; the mechanism and the
two invariants a probe owes are in the Kiln WEP. Loam's probe reads a
safetensors header, which satisfies both. The header length is in the first
eight bytes, so the extent is determined by bytes inside it.

Without it the build would hash whole checkpoints on every incremental build,
proving that bytes the output never depended on did not change.

The graph file is probed too, and its extent is the whole file, since every byte
of a textual graph is schema. An extent is a prefix, so a format that
interleaves its schema with its data has none, and this is what a protobuf
`.onnx` does: graph and initializers in one message, interleaved, so no prefix
excludes the weights. A model whose weights are large must therefore keep them
in external data files, which is
`onnx.save_model(..., save_as_external_data=True)` and is what every model over
2 GB already does, since protobuf caps a message there. A stated input
requirement is what keeps the extent a length instead of a range set; the
alternative was generalizing the extent so one input could name several disjoint
ranges, which complicates the key, the record, and every generator that never
needed it.

Loam is the reason Kiln's probe receives the invocation's options:
`inline_weights` makes the output depend on the whole file rather than on the
header, so a probe blind to it would either report the whole file every time,
losing what the extent was for, or report the header and let a payload-only
change hit the cache and emit a module carrying the old weights.

Per-input probing is what a real checkpoint needs. Large models ship sharded —
`model-00001-of-00003.safetensors` beside an index — so several huge inputs
arrive at one invocation, each with a header of its own.

The generated module contains the typed graph, the kernels, and a loader that
checks the incoming payloads against the shapes the header declared. A
checkpoint that does not match its header reports which axis disagreed, at load
time, rather than producing wrong numbers.

A small model may set `inline_weights` to have the payload emitted as a byte
string literal read by `List::from_le_bytes`, which makes the component
self-contained. The compiler folds that call into a data segment, so the Wasm
grows by the payload alone and loading it runs no decode loop. This is for test
fixtures and small models, not the normal path. A `.onnx` carrying its own
weights takes the same path, and costs the cache nothing, since its extent is
the whole file already.

The literal was chosen over the alternatives by measurement. A float literal
per element costs every compiler phase a node, about 11 s and 460 MB per MiB.
A decode at startup, from protobuf, base64 in `__DATA__` or zlib, costs 8 to
40 ms per MiB and grows the Wasm or the startup. The folded byte literal
compiles at under 1 s per MiB and loads in one `array.new_data`.

### Axis Identity Is a Type, Extents Are Values

An axis has a name rather than a position. Transposition is then a change of
description rather than a movement of data, and an operation states which axes
it consumes.

An axis is a marker type, and a tensor carries its axis list as one type
parameter: `Tensor<f32, [Batch, Seq]>`. Naming the same axis variable twice in
a signature makes the two positions agree, so a contraction checks itself:

```wado
fn matmul<M, K, N>(a: &Tensor<f32, [M, K]>, b: &Tensor<f32, [K, N]>) -> Tensor<f32, [M, N]>
```

`example/tensor_axes.wado` is the working form, with a forward pass built on it.
Rank-generic operations take the axis list as a plain type parameter, and an
operation that changes the rank destructures it with a pack, so a reduction is
`<..Rest, Last>(t: &Tensor<f32, [..Rest, Last]>) -> Tensor<f32, [..Rest]>`.

This needs no language change. It was the open question when this WEP was
written, because Wado has no const generics, and it is closed: an extent cannot
be carried in a type, but an axis identity can, and that is the half that
catches the mistakes people actually make.

Extents therefore stay runtime values, and stage 0 is what checks them. A static
extent is a `dim_value` the graph states, and a checkpoint's header is checked
against it. A dynamic extent, such as sequence length or batch size, is a named
symbol that stage 0 carries through the shape algebra without knowing its value.
Stage 0 counts two tensors carrying one symbol as the same length. The caller
owes that, and a kernel that finds otherwise traps.

Errors split across the two layers. The generated boundary carries these types,
so a caller passing the wrong tensor gets a type error from the ordinary
compiler. A disagreeing extent inside the graph, or between the graph and its
checkpoint, is discharged as compile-time computation in the generator, which is
the ECOOP 2026 formulation.

An extent condition that stage 0 cannot discharge is a compile error. Loam has
no runtime tier to defer it to, because the MVP has no tier below the static
one. This is the MVP's boundary, stated rather than worked around.

The generated module writes each axis as a marker type and the tensors in terms
of them, so a caller says `Tensor<f32, [Batch, In]>` where it means the input.
It emits no per-tensor alias. Wado's `type` is a newtype, so an alias would need
an `as` at every construction to restate what the axis list already says, and it
would make two tensors of one shape distinct for no reason.

### The Axis Schema Is an Invocation Option

Neither the graph nor the checkpoint says which axis is the batch. An ONNX shape
and a safetensors header both give a tensor's rank and its lengths and nothing
about what they mean. Axis names are a property of the architecture rather than
of either file: two Llama checkpoints of different sizes share their axis names
and differ only in their extents.

So the architecture is named where the graph is named, in the invocation's
options:

```wado
use { Weights, forward } from "./model.onnxtext" with {
    generator: {
        module: "wado-lang:loam@0.1",
        inputs: ["./model.safetensors"],
        options: {
            architecture: "llama",
            layout: [{ pattern: "*.q_proj.weight", axes: ["Hidden", "Hidden"] }],
        },
    },
};
```

`layout` is what the generator reads. `architecture` is not read at all: it
names the built-in table a tensor falls back to where no pattern reaches it,
and roadmap step 8 writes those tables.

Options rather than a second file, because Kiln already rejected a schema a
reader has to go elsewhere to find (§"A manifest-side invocation registry").
Options are typed by the generator's own `Options` struct, so the use site gets
validation and completion that a sidecar document could not have, and they are
canonically encoded into the cache key, so reformatting one does not regenerate.
Kiln's probe receives them too, which `inline_weights` needs.

Naming every tensor is not an option at either place. A thirty-layer
transformer has hundreds, so the schema is a name and a set of patterns:
`architecture` selects a table Loam ships, and `layout` holds patterns consulted
in order ahead of it. A pattern is a shell wildcard over the tensor's name, and
the first rule that matches wins, so one pattern overrides a table entry without
restating the rest of it.

The schema names the graph's inputs and its initializers. Every other value
takes its axes from the operator that produced it, and an ONNX `dim_param` or
`?` on a named axis becomes a symbolic extent standing for that axis. An axis an
operator creates is the exception, and the next section names it.

A tensor that neither reaches is a build error naming it. Loam does not fall
back to positional axes, for the same reason stage 0 does not fall back to a
runtime check.

The tables age, because model formats move. That is safe rather than merely
accepted: a table is read at build time and its answer is baked into the
generated module, so a stale one stops the build with the error above instead of
producing a module that computes the wrong thing.

`architecture` is an option rather than something read from the file.
safetensors has only a free-form `__metadata__` map, which carries no dependable
architecture. A format that does state one, as GGUF's `general.architecture`
does, can have it read and checked against the option.

### A Regrouped Axis Is Named by Its Parts

`Flatten`, `Reshape` and `Unsqueeze` produce axes that no input carries. Most of
them are regroupings, and a regrouping names its result from its parts.

Merging adjacent axes produces one axis whose identity is the ordered list of
its parts, `Merged<[C, H, W]>`, and whose extent is their product. Splitting
it again yields the parts back. A `Reshape` in general takes its input apart
into those parts and gives each output axis the consecutive run of them whose
extents multiply to its own, so a merge followed by a different split is still
named.

`layout` writes a merged axis as einops does, `"(C H W)"`. A weight that reads a
flattened activation, as the first dense layer after a convolution does, names
the axis it contracts that way, and the contraction checks as any other does.

An axis that no regrouping determines is new: the split of an axis that was
never merged, the extent-1 axis `Unsqueeze` inserts, and the axes of a
`Constant` with more than one element. The schema names those. A `layout`
pattern reaches a node's output by its tensor name, and it is consulted only for
an axis the operator left undetermined. One that no pattern reaches stops the
build naming the tensor. A generated name would be the positional fallback the
previous section refuses.

Two things follow. An extent is a product of symbols as well as a symbol, since
the parts of a merge may be dynamic. And `Reshape` reads its target shape at
build time, so the generator reads an integer tensor, which the graph carries as
a `Constant` or an initializer.

### The dtype Is a Storage-Only Primitive

A checkpoint's elements are mostly half precision, and most LLM checkpoints on
the Hub are bf16. Wado computes in neither, and Loam never asks it to: the
host's job is to move the bytes. So `f16` and `bf16` are primitives that carry
bits and no arithmetic. Adding them is a compiler change rather than a Loam one,
specified in
[WEP: Half-Precision Primitives](./wep-2026-09-22-half-precision-primitives.md).

Loam holds such a tensor and never computes in it. A graph whose boundary is
`float16` or `bfloat16` gets a `Weights` and a `forward` typed in that
primitive, and `forward` widens each half operand into f32 on the way in and
narrows the result on the way out. The kernels see one element type, so a
kernel signature states its axes and no dtype.

A dtype becomes a Wado primitive only where a tensor of it can cross the
generated module's boundary, as an input embedding or an output logit does. A
weight-only format never does. int4 is two elements to a byte with a scale per
block, and f8 is never shipped without its scales either; WGSL has no type for
either and unpacks both from `u32` with shifts. They stay bytes in the
checkpoint and a tag inside the generator, and never reach Wado's type system.

### The Signature Is the Notation

einx exists because Python cannot say in a type what an operation does to a
shape, so it says it in a string. Wado can say it in a type. The runtime
declares each kernel, and the generator the model's boundary, as a generic
signature that carries every part of the notation:

```wado
fn matmul<..Bs, M, K, N>(
    a: &Tensor<f32, [..Bs, M, K]>,
    b: &Tensor<f32, [..Bs, K, N]>,
) -> Tensor<f32, [..Bs, M, N]>
```

A repeated variable is einx's bracket: `K` appears in both operands and not in
the result, which is what contraction means. The unrepeated scalars are the
vectorized axes, the pack is einx's leading ellipsis, and the return type is its
arrow. One signature covers rank 2, 3 and 4, because the pack also matches
empty.

So there is no notation layer. A tagged template could not have been one
anyway: `ReflectTemplate` exposes the hole _types_ and the literal text as a
_value_, with no associated type derived from the literal, and einx's entire
content is in that literal. A tag could only return a tensor whose axes had
been erased, discarding what the type layer just won.

A parameter list may declare several packs, each settled by the argument that
carries it. So an operation whose input and output axis lists are independent
names both, which is what a rank-changing operator such as `Reshape` needs.

A contraction names its axis where the axis sits. Two packs in one tuple settle
neither on their own, so `[..Pre, K, ..Post]` needs its ends settled by something
else, and a generated call spells them in a turbofish. The generator writes both
sides of that call, so spelling them costs it nothing.

Whether a middle-axis contraction is then transposed into the trailing position
is the kernel's decision, taken for locality rather than forced by the signature.
A rank-2 weight broadcasts across batch axes by putting a pack on one side only.

### The Backend Is a Trait

A `Backend` trait, monomorphized at each use, selects where kernels run. The
MVP ships one implementation, on the CPU.

An effect was considered and set aside. Wado's effects lower through stack
switching, whose per-operation cost is unmeasured here, and a tensor dispatch is
a hot path. A trait's cost is known to be zero.

The CPU backend is for correctness and for the seam, not for speed. Wasm SIMD
loads from linear memory and a Wado `List<T>` is a WasmGC array with no address,
so `core:simd` offers no load: a vector is built by `splat`, by tuple coercion,
or by reinterpreting another vector. The pattern that does pay is `core:prng`'s,
where vectors stay in the dataflow and never come from a list, which suits a
tile held across a long computation and little else. The performance story
belongs to the GPU backend, and a place with no GPU, such as an edge worker, is
not a target until the CPU path has a vector load.

### The MVP Is Tier 1 Only

Gale's two tiers become three here. This WEP builds the first:

| Tier              | Decided at        | Covers                               |
| ----------------- | ----------------- | ------------------------------------ |
| Static (tier 1)   | build time        | Static shapes, weights, fused blocks |
| Bucketed (tier 2) | first use, cached | Residual sequence and batch extents  |
| Dynamic (tier 3)  | per token         | MoE routing, speculation, early exit |

Tiers 2 and 3 are deliberately absent, not undiscovered.

Tier 2 is a shape-class cache rather than a simulator. Generating a kernel is
expensive where Gale's ATN step is cheap, and the generation must finish before
the dispatch it serves can run. Tier 3 is the genuine analogue of Gale's ATN:
data-dependent control flow that no bucketing covers.

### The Generator Reports Every Fusion Decision

`gale dump` is what makes Gale's escalation auditable, and its absence is why
`torch.compile`'s graph breaks arrive as a mystery. Loam's generator reports,
per operation, what it fused, what it did not, and why.

The MVP has one tier and reports anyway. A declined fusion carries the reason
it was declined, and those reasons are what will route the later tiers.

### Every Name Is Minted From One Set

Every identifier the generated module declares is minted from one set. The
module binds the kernels it inlines, `forward`, `Weights` and the `weights`
parameter before it names anything the graph brings, and the runtime's share is
read out of the runtime source, so a declaration added there is reserved
without anything else being edited.

The two kinds of name the graph brings are answered differently. An ONNX tensor
name is any string and comes out of a model file, so `weights`, `map` and
`Batch` are all names a graph may carry, and one that is taken gets a trailing
`_`. An axis name is the schema's own word, so an axis named after a kernel or a
marker stops the build naming it: renaming it silently would rewrite what the
author wrote, and they are there to change it.

The language's own share of that set is `package-wadopoet`'s `is_reserved`: every
keyword the parser does not take as a name, and every name the prelude puts in
scope. A name keyword such as `type` or `from` stays free. The predicate is
generated from what `wado syntax --format json` reports, so a keyword added to
the compiler is reserved here without anything else being edited. Gale reserves
the same set for a grammar's rule names.

### What the CPU MVP Cannot Validate

The MVP validates the shape algebra, the generator architecture, and the backend
seam. It does not validate the fusion objective.

On CPU the objective is memory traffic. On WebGPU at batch size 1 it is dispatch
count. They are different objectives, and a fusion policy tuned against the
first is not evidence about the second. The GPU WEP will have to re-derive its
policy from measurement rather than inherit this one.

The CPU arm cannot even reach its own objective's ceiling, for the reason in
"The Backend Is a Trait": no vector load from a WasmGC array. A number this MVP
produces is a correctness result and a floor, never a claim about the design.

## Roadmap

1. [x] The kernels. Each operator lowers to a call into the inlined
       runtime (`package-loam/src/runtime/tensor.wado`), and the generated module
       carries a `Weights` struct for the graph's initializers and a `forward` that
       runs the nodes in order. Each kernel carries the axis notation in its own
       signature. `matmul<..Bs, M, K, N>` contracts `K`, and
       `zip_suffix<..Pre, ..Suf>` broadcasts a trailing axis list, so a generated
       call is checked by the ordinary compiler rather than by Loam. What each
       kernel covers is narrower than what stage 0 checks, and a node outside it
       stops the build naming the operands; the gaps below say which.
       `package-loam/conformance/` checks them against ONNX's own outputs: graphs
       from the backend test data compile through Loam and reproduce the tensors
       shipped beside them. The models are committed under
       `package-loam/tests/onnx/`.
2. [x] The half-precision element types. `float16` and `bfloat16` map to the
       primitives [WEP: Half-Precision Primitives](./wep-2026-09-22-half-precision-primitives.md)
       adds. `Weights` and `forward` state the graph's own element type, and
       `widen` / `narrow` convert at the boundary over the `Held` trait the
       two halves implement. `package-loam/example/half.wado` compiles such a
       graph through Kiln and prints its tensor.
3. [x] A model's own weights. Where a graph carries every initializer's data,
       the generated module adds `Weights::embedded()`, which returns them. Each
       payload is a byte literal read by `List::from_le_bytes`, which the
       compiler folds into a data segment, so an ONNX file alone is enough to
       run inference. The conformance graphs with initializers run from
       `Weights::embedded()`.
4. [ ] Minimal inference on ONNX alone. The operators and ranks a small real
       model needs. Finished when that model runs from its `.onnx` file and
       reproduces the output shipped beside it, as the conformance graphs do.
5. [ ] The checkpoint reader. safetensors in the generator, its header checked
       against the graph. safetensors comes first because its header is already
       JSON, with no quantization to model. The generated loader checks each
       payload against the shape its header declared. Finished when a real
       checkpoint's shapes check against its graph and its payloads load, and a
       deliberately mismatched header or payload names the axis.
6. [ ] The backend seam. The `Backend` trait with its CPU implementation. Finished
       when the MLP runs through the trait and matches the reference within
       tolerance.
7. [ ] Fusion and its report. The generator fuses operators into one kernel
       where the CPU objective favours it, and reports each decision, following
       what `gale dump` established. Finished when the step-4 model runs with its
       elementwise chains fused and matches the unfused output, and every
       operation reports a decision and a reason.
8. [ ] The architecture tables. `architecture` selects one Loam ships, consulted
       after the `layout` patterns. Finished when a Llama checkpoint needs no
       `layout` entry to name its axes.
9. [ ] The StableHLO front end. Finished when the MLP exported from JAX checks and
       runs through the same pipeline as its ONNX form.
10. [ ] int4. `DequantizeLinear` with a `block_size` fused into the `MatMul` it
        feeds, which is what makes a model small enough to download. Finished when
        an int4 checkpoint from GPTQ or AWQ produces the f16 checkpoint's output
        within tolerance.

## Known gaps

The operator set is `MatMul`, the binary and unary elementwise operators, a
`Transpose`, a `Gemm` lowered to those kernels rather than to one of its own,
and a `Constant` of one element, which is folded into the closure of whatever
reads it rather than becoming a tensor. The shape algebra takes a `Transpose` at any rank and
its kernel reaches only rank 2, since a permutation of three or more axes is not
one generic signature: each of the `n!` orders is its own type. A `Constant`
carrying more than one element stops the build, since `layout` does not yet
reach a node's output to name its axes. A one-element `Constant` is
rank 0 whatever shape the tensor declares, so one of shape `[1]` loses that
axis, and a graph declaring an output of that rank stops the build rather than
producing a wrong number. Folding a constant needs a closure the reader already
writes, so two operand positions take one: a binary
elementwise operand whose partner is a tensor, and a `Gemm` bias. Anywhere
else stops the build naming the constant, a graph output included. Every other
operator stops the build naming itself, so a transformer does not check: it
needs at least `Reshape`, `Softmax`, and the normalizations.

A node produces one output. `Split`, `TopK` and the recurrent operators name
several, and stage 0 has one slot per node to put a shape in. A graph produces
one too: `forward` returns a value, and a graph naming several outputs stops the
build.

The kernels cover less than stage 0 checks, and the difference is a build error
rather than a wrong number. `matmul` takes two operands of one rank sharing one
batch axis list, so ONNX's rank-1 promotion and its broadcast batch axes have no
call to write. An elementwise operator takes two operands whose axis lists are
equal, or whose shorter one is the longer's trailing run, so a stretch of an
extent-1 axis in the middle has none either. Two axes agree for a kernel only
when they agree on the extent as well as the name, since stage 0 lets an extent
of 1 yield to the other operand and leaves the name standing. Each of these is
the kernel's signature being narrower than the shape rule, so closing one is a
kernel and its call, never a change to stage 0.

Every kernel computes in f32. A boundary of `float16` or `bfloat16` is held in
that primitive and widened, and every other element type stops the build naming
it. `double` and the integer types are a second instantiation of the same
kernels. Wado has a primitive for nearly every ONNX element type, so what a step
adds is kernels that compute in one, never the mapping.

A half-precision weight is widened on every call to `forward`. Nothing holds a
graph's weights between calls, so the conversion has no earlier place to happen,
and a caller in a loop pays it each time. Hoisting it needs a type standing for
weights already prepared, which is the same seam the checkpoint reader fills.

The conformance suite reaches the graphs ONNX commits, not the per-operator
cases. `onnx/backend/test/data/node` is generated rather than checked in, so
what `package-loam/conformance/` runs against is `pytorch-operator/` and
`pytorch-converted/`: whole small graphs with their inputs and outputs beside
them. An operator no committed graph exercises is still pinned by hand-written
cases, which test what Loam believes the operator means.

Those models are copied into `package-loam/tests/onnx/` rather than read out of
`vendor/onnx`. A submodule is absent wherever it is not initialized, and a file
an import names has to be there for the module to compile, so reading one turns
a test into a build failure. The copies keep the upstream layout, and the
directory's `README.md` carries the provenance.

A binary model's extent of zero reads as `?`. `TensorShapeProto.Dimension` is a
`oneof`, so the file records which of `dim_value` and `dim_param` it set.
`core:protobuf` has no `oneof`, so a `dim_value` of `0` reaches the reader as
the absent field. The textual reader keeps the distinction, since a written `0`
is a token.

The opset a model declares is not read. `opset_import` says which operator
versions the graph is written against, and the shape rules assume one without
consulting it, so a graph from an opset whose rule differs is checked against
the wrong rule and says nothing about it.

Only `Transpose`, `Gemm` and `Constant` read their attributes. The readers carry
every attribute as the text it was written as, and `perm`, `alpha`, `beta`,
`transA`, `transB` and `Constant`'s `value` are the ones a stage consults, so
every other operator is checked as if its attributes were absent. A tensor
attribute is carried only when its elements are float, so a `Constant` of any
other type stops the build as one with no `value` would.

An initializer naming its own data file stops the build, naming the tensor. The
textual format lets one carry a `["location": ...]` list, the protobuf form an
`external_data` entry, and Loam takes its weights from the
checkpoint the invocation names, so the two say different things about where
one tensor's bytes are.

The grammar has no `nan` or `inf` literal, which `onnx.parser` reads as a float,
so a textual graph carrying one does not parse.

Tier 2, the bucketed JIT. Residual sequence and batch extents need a
shape-class cache populated on first use. Closing it needs a cache key design, a
warmup story, and an answer to generation latency becoming user-visible. At
build time no user waits on the generator; at first use one does.

Tier 3, dynamic dispatch. MoE routing, speculative decoding, and early exit are
data-dependent and no bucketing covers them. Closing it needs the escalation
boundary drawn as a decidability question, as Gale's is, rather than as a
heuristic.

The GPU backend. A second `Backend` implementation over `wasi:webgpu`, with the
fusion objective re-derived for dispatch count. This is a WEP of its own. A
`benchmark/` row against onnxruntime waits for it, since a CPU number is only a
floor.

Quantization beyond int4. Block formats are parameterized by block size, scale
representation, and rotation, so the type that carries one must be
parameterized the same way rather than named after a format; f8 belongs here,
since it is never shipped without its scales. GGUF as an input format arrives
with this, not before it, and its metadata is a binary key-value block rather
than JSON, so its probe has to parse one to report an extent.

ONNX local functions. The textual format lets a model carry its own function
definitions and call them as operators, and the grammar covers neither, nor the
`@name` attribute reference only a function body can carry, so a model holding
one does not parse. What they admit is an operator set a model brings with it
rather than one Loam knows, which the shape algebra has no account of.

Loam has no probe yet, so its build keys on whole files. A probe alone would
not stop the read: an extent saves hashing the bytes past the header, not
reading them, so a gigabyte checkpoint is loaded in full on every build. The checkpoint reader is the first caller that
makes this visible; the Kiln WEP records what closing it takes.

Training. Loam is an inference design. An autograd layer over the same shape
algebra is plausible and unowned.

Whether the backend should be an effect after all. The trait is chosen because
its cost is known to be zero and the effect's is unmeasured. A second backend
makes the measurement possible.
