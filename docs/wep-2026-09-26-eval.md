# WEP: Eval — Compiling and Running Wado Source from a Test

## Context

A code generator is tested by compiling what it generates and running it. Gale
does this today one grammar at a time. Each test file names its grammar at a
`use ... with` site, the generated parser is written to a `generated/`
directory, and the test calls into it:

```wado
use wa from "./grammars/wado_action.g4"
    with {
        generator: { module: "../src/generator.wado", output_dir: "./generated/action_emit" },
    };

test "wado actions emit into ParseResult.output in execution order" {
    assert wa::parse("a b").output == "hi!";
}
```

In `package-gale/tests/`, 316 files carry such a use site, and
`tests/generated/` holds the 740 parsers they produce. The ANTLR4 descriptor corpus is
the worst fit. It is data: a grammar, an input and the expected output, many
times over. Yet a script has to write it out as test files, one use site and one
output directory per descriptor, because a use site is the only way to turn
source text into a program.

What these tests want is a function. It takes generated source, compiles it as a
program, runs it, and returns what the program printed. Rust's `trybuild`
answers the same need.

## Decision

### `core:eval` compiles and runs a program

`core:eval` exports one function and the types it takes and returns:

```wado
pub struct Output {
    pub stdout: String,
    pub stderr: String,
    pub status: Status,
}

pub variant Status {
    Exited(i32),
    Trapped(TrapKind),
    OutOfFuel,
    OutOfMemory,
}

pub enum TrapKind { ... }     // one case per trap the engine reports

pub struct CompileFailure {
    pub rendered: String,     // the report `wado compile` would print
    pub codes: List<String>,  // the `Code` of each error, in report order
}

pub variant EvalError {
    CompileFailed(CompileFailure),
    CompileTimedOut,
    Unavailable(String),      // the import the host refused to link
}

impl Display for Status { ... }
impl Display for TrapKind { ... }
impl Display for EvalError { ... }
impl Error for EvalError;

pub global DEFAULT_FUEL: u64 = /* chosen by the implementation */;

pub fn eval(source: String, fuel: u64 = DEFAULT_FUEL) -> Result<Output, EvalError>;
```

A test uses it like any other function:

```wado
use { eval } from "core:eval";

test "a generated parser accepts its input" {
    let parser = generate(grammar);  // the generator under test, called as a library
    let program = `use { println, Stdout } from "core:cli";
${parser}
export fn run() with Stdout { println(parse("a b").output); }`;
    let out = eval(program).unwrap();
    assert out.status matches { Exited(0) }, `${out.status}\n${out.stderr}`;
    assert out.stdout == "hi!\n";
}
```

`CompileFailure` carries a failure the way an e2e fixture states one: as the
whole report or as the codes it was raised under. A test can then check that a
generator rejects bad input with the right error, not only that good input runs.

The split between `Ok` and `Err` is whether the program ran. `Err` means it never
started, so there is no output to read. `Ok` means it ran, however it ended:
`Status` says how, and `stdout` and `stderr` hold everything it wrote before
then. A trap is where that matters most. What a failing program printed is what
explains the failure, and a `panic` writes its message to stderr before it
traps.

`EvalError` implements `Display` and `Error`, as every standard library error
type does, so `${e}` renders the compile report or the missing import. `Status`
and `TrapKind` implement `Display` too, for an assertion's message.

### The host does only what Wado cannot

The host import is kept to what Wado code cannot do: compile the source, run
it, and cache the outcome. It returns the outcome as raw data. Captured output
crosses as bytes, a trap as a `TrapKind` case, and a compile failure as the
rendered report and its codes.

`core:eval` does the rest in Wado. It decodes stdout and stderr with
`String::from_utf8_lossy`, so a program writing bytes that are not UTF-8 still
yields a `String`, with U+FFFD where the invalid bytes were. It shapes the raw
outcome into `Result<Output, EvalError>`, and it holds every `Display` impl.

### The program is one module

`source` is the whole program, compiled as a single module. Its `use` items may
name `core:*`, which resolves to the standard library. Any other specifier fails
to compile, a relative path included, since the module has no directory. Nothing
on the host's disk is read.

This is enough for Gale, which emits one module per grammar with its runtime
inside. A program spread over several modules, and one that imports the calling
package's dependencies, are known gaps.

### The program runs as a command and gets nothing

The program is compiled for `wasi:cli/command`, so it exports `run()` and uses
that world's bump allocator. Only stdout, stderr and exit are linked, and the
first two are captured. It receives no arguments, no stdin, no environment, no
preopened directory, no clock, no randomness and no network.

A program that imports anything else is not linked. `eval` returns
`Unavailable` naming the import, instead of trapping the calling test.

Giving the program nothing is what makes its result a function of its source.
The result cache below depends on that.

### Every resource is bounded

The run is bounded by `fuel` and by a memory ceiling the runner sets. A program
that uses up either stops with `OutOfFuel` or `OutOfMemory`. Neither bound is
wall-clock time, so where a program stops is deterministic too.

The compile is bounded by wall-clock time, because a compiler bug can make it
loop. Past the runner's limit, `eval` returns `CompileTimedOut`. How far a
compile gets in that time depends on the machine, so this outcome is never
cached.

These bounds replace the calling test's timeout inside `eval`. A first run
compiles every program it evaluates, and that alone can exceed the default
5000 ms, so time spent inside `eval` does not count against the test's deadline.

`eval` runs on the calling test's CPU permit and takes no other. The test is
blocked inside `eval`, so the permit it holds is exactly the CPU the compile
uses. The runner neither deadlocks on its own budget nor runs more work than
the budget allows. A call waiting on another call's slot holds its permit while
it waits, which costs parallelism only when two tests evaluate the same source
at once.

### Only `wado test` supports it

`eval` is a testing tool, not a general capability. A program built for any
world other than the test world that reaches `core:eval` is a compile error.
Without that check, the component would build and then fail to instantiate
wherever it runs.

`wado test` is the only host that supports it. No other host supplies the
import: not the LSP, not jco, and not another runtime handed the `.wasm`. A
component reaching `core:eval` fails to instantiate on any of them. The LSP
still type-checks a call to `eval`, since that needs no host, but it never runs
one. `core:eval`'s own tests are ordinary stdlib tests, run by `wado test` like
the rest.

`eval` declares no effect, as `log_stdout` declares none. In a test, an effect
row would say nothing the world has not already said.

### The program compiles as the test does

The program is compiled at the calling test's optimization level and with its
`-f` flags. A CI job that runs a package's tests at `-O2` then checks the
generated code at `-O2` too.

`--allocator` is not carried over, because the program is a command and uses the
command world's allocator. `--no-cache` makes `eval` skip reading the cache
below, as it makes a compile skip Kiln's.

### Every outcome is cached

wasmtime's AOT compile is most of an evaluation's cost, and running the result
takes almost no time. So the cache holds the outcome: the raw data the host
import returns, before `core:eval` decodes it. A hit does not compile,
instantiate or run anything.

The key covers everything the outcome depends on:

- the hash of the running `wado` binary, which links both the compiler and
  wasmtime,
- the hash of the standard library sources the compiler reads, because a dev
  build reads them from disk at run time, and editing one does not move the
  binary's hash,
- the optimization level and the `-f` flags,
- the fuel budget and the memory ceiling,
- the source.

Every ingredient is known before anything runs, so the key is exact on the first
run. Kiln's cache is exact for the same reason.

The compiler is part of the key, although Kiln leaves it out of its own. What a
test checks with `eval` is that the current compiler builds and runs the
generated code. If a stale hit survived a compiler change, the test would stop
checking that.

The cache never leaves the machine that wrote it, so an outcome has to repeat
only on that machine. It does so even where Wasm leaves a result to the host,
such as a Relaxed SIMD instruction or the payload of a NaN, because the same
engine on the same machine decides the same way each time.

Outcomes live in `build/eval/` under the calling file's package root, or under
the calling file's directory when it is in no package. The directory is not
committed. The key moves with every compiler change, so a committed cache would
miss after nearly every commit. Losing the cache is never an error.

Within one `wado test` run, calls that share a key share one slot. The first
call evaluates, and the others wait for its outcome, so the same program is
never compiled twice at once.

## Alternatives considered

### Keep one use site per program

This is how the tests work today. It fits a hand-written test well, but it cannot
iterate over data, and it adds a generated directory for every case.

### Spawn `wado run` from the test

The test world has no process API, and adding one would give every test far more
than it needs. It would also pay the AOT compile on every run, with no cache to
skip it.

### Evaluate inside a Kiln generator

A generator is already a Wado program, so anything `eval` could compute there,
the generator can compute directly. The one new thing `eval` would give it is a
check that its output compiles, and the compiler makes that check right after
the generator returns.

### Cache the compiled component only

This caches the cheap half. The AOT compile, which is the expensive half, would
still run on every call.

## Roadmap

1. `core:eval`: the host import and its raw outcome, the types, `eval` with its
   decoding and `Display` impls, and the compile error for a program outside
   the test world.
2. The host, in the `wado test` runner: compile the source under a
   time limit and on the caller's CPU permit, link stdout, stderr and exit
   only, run under fuel and a memory ceiling, and return the raw outcome.
3. The outcome cache: the key, `build/eval/`, `--no-cache`, and one slot per key
   within a run.
4. The deadline: time inside `eval` stops counting against the calling test.
5. The pilot: rewrite Gale's ANTLR4 descriptor tests as a loop over the corpus,
   in place of the test files the extract script writes, and remove the output
   directories they no longer need.

## Known gaps

- [ ] The program is one module. A generator whose output spans several modules
      cannot be evaluated.
- [ ] The program cannot use the calling package's dependencies. A generator
      whose output imports a package cannot be tested with `eval`.
- [ ] The program receives no arguments, stdin or environment.
- [ ] The program can only be a command. A `wasi:http/service` handler cannot be
      evaluated.
- [ ] Changing only the fuel budget or the memory ceiling misses the cache and
      pays the AOT compile again, though the component itself did not change.
- [ ] `build/eval/` is never pruned. Outcomes keyed by an old compiler stay until
      the directory is removed.
