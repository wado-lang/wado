# WEP: Grog — Protocol Buffers for Wado

## Context

Loam reads a model graph, and the form every exporter writes is protobuf.
[WEP: Loam](./wep-2026-09-20-loam.md) records the consequence twice. A `.onnx`
model has to be converted to text outside the build, and the ONNX backend test
data, which is the oracle its kernels are supposed to be checked against, cannot
be read at all. Both are the same missing piece.

Wado already has the framework a format plugs into. `core:serde` derives
`Serialize` and `Deserialize` from a plain struct, and `core:json`, `core:cbor`
and `core:json_nsd` are three formats over it. The third one settles the
question this WEP would otherwise have to open: `core:json_nsd` is
non-self-describing, encoding a struct as a positional array with the field
names dropped. A wire form that carries no names is not new here.

Protobuf is two things that ship as one. There is a wire format, which is a tag,
a wire type and a value, repeated. It is small, it is stable, and it needs no
schema language to implement. And there is `.proto`, a schema language with a
grammar, which is what `protoc` compiles. Only the second needs a parser.

Both halves are specified, and `vendor/protobuf-spec` is the specification:
`content/programming-guides/encoding.md` is the wire format and
`content/reference/protobuf/proto3-spec.md` is the grammar. The rules come from
there rather than from an implementation, as Loam's operators come from ONNX.

That split decides where each half lives. Parsing `.proto` means a grammar, and
a grammar in this tree means Gale, which is a package rather than stdlib.
Anything that reads `.proto` inherits that and cannot be `core:*`. The wire
format inherits nothing, and it is the half every consumer actually needs.

## Decision

### `core:protobuf` is the wire format, Grog is the schema language

`core:protobuf` is a stdlib serde format beside `core:json` and `core:cbor`. It
encodes and decodes the protobuf wire format against ordinary Wado
declarations, and it reads no `.proto`.

Grog is a package. It parses `.proto` with a Gale-built parser and emits the
Wado declarations `core:protobuf` encodes. It is a Kiln generator, invoked the
way Gale's is.

A consumer that can write its messages by hand needs only the stdlib half. Loam
is one: it reads a fixed subset of ONNX's schema, and that subset is a few
structs. So Loam depends on `core:protobuf` and never on Grog, and the
conformance gap closes without waiting for a schema compiler.

### The name

Grog is fired clay, ground up and mixed back into raw clay so a mould holds its
shape through the firing. A `.proto` is a schema fired elsewhere. Grog grinds it
into Wado declarations, and Kiln fires the result. The name is a short natural
noun, as Gale, Kiln, Jade, Marl and Loam are.

### Grog emits declarations, not codecs

What Grog writes is `struct`, `variant` and `enum` declarations carrying wire
attributes. It writes no encoder, no decoder, and no runtime.

This is what removes version drift between generator and runtime, and it does so
more cheaply than Gale does. Gale inlines its runtime into every generated
parser because its output is code, and code and runtime can disagree. Grog's
output is data-shaped: a declaration says which field carries which number, and
`core:protobuf` reads that the same way whoever wrote it. A hand-written message
and a Grog-generated one are the same kind of thing.

### `#[wire(number = N)]` carries the field number

Protobuf identifies a field by a number rather than a name, so the number has to
reach the serializer. `#[wire(...)]` already carries a format's per-field
adjustments, and `#[wire(name = "type")]` already overrides the string key on
the wire. The numeric key is its sibling:

```wado
struct Point {
    #[wire(number = 1)]
    x: i32,
    #[wire(number = 2)]
    y: i32,
}
```

It is `number` rather than `index` because that is what the protobuf
specification calls it, and because the two words mean different things. An
index is positional, zero-based and dense. A field number is none of those: it
starts at 1, it is sparse, and reordering the fields does not change it. That
stability is the whole point of the format, so naming it after position would
teach the opposite. It also leaves `index` free for a genuine position, which is
what a non-self-describing format like `core:json_nsd` would want if it ever
takes an explicit one.

There is no `number_policy`. A policy would assign numbers from the declaration,
and a field inserted in the middle would silently renumber everything after it,
which is exactly the wire break protobuf exists to prevent. A number is always
written.

A struct carries numbers on every field or on none. One numbered field says the
type is meant for the wire protobuf describes, so a sibling without a number is
a mistake in the declaration, and the compiler says so where the type is
written. A partly numbered struct therefore never exists, which is what lets
everything below decide per type rather than per field. A struct with no fields
satisfies the rule with nothing to check, and encodes as the empty message
protobuf reads it as.

### How a number reaches a format

A numbered type still serializes to JSON. `#[wire(number = 1)] x` has to produce
`{"x":1}` through `core:json`, so a format cannot be told at its own boundary
which shape it speaks: the derived `serialize` body is one generic body over
`S: Serializer`, and it drives whichever serializer it is given.

So `SerializeStruct` gains a method rather than a sibling trait, and its default
implementation drops the number:

```wado
fn field_numbered<T: Serialize, S: AsStrSlice>(
    &mut self,
    number: i32,
    name: S,
    value: &T,
) -> Result<(), SerializeError> {
    return self.field(name, value);
}
```

The derivation emits `field_numbered` for a numbered type and `field` for every
other, so a type carrying no numbers emits the calls it emits today and nothing
about any existing format changes. A numbered type reaching a name-based format
pays one constant argument that the default drops, which monomorphization folds
away. `core:protobuf` overrides the method and receives the number as a constant
at the call site, with no lookup and no per-field state.

Decoding reads `FieldSchema`, which already answers `lookup` for a wire name and
`positional_at` for an ordinal. A number is the third question, `by_number`,
synthesized beside them and resolved statically the same way. `core:protobuf`
never calls `lookup`.

### A numbered type is a bound, not a runtime check

`core:protobuf`'s entry points require a marker the compiler synthesizes for a
type whose fields all carry numbers:

```wado
pub fn to_bytes<T: Serialize + WireNumbered>(value: &T) -> Result<ByteList, SerializeError>
```

Passing a type without numbers is then a bound error where the call is written,
rather than a failure when the bytes are produced. The marker is empty, so it
costs nothing at run time, and it is the same bound-driven derivation
`Serialize` itself uses. Where a name is reserved rather than absent,
`#[unavailable("…")]` carries the sentence saying why.

This is what keeps the protobuf path free of dynamic checks: no per-field
branch, no name comparison, no search for a number.

### The type mapping

| Protobuf                        | Wado            |
| ------------------------------- | --------------- |
| `double` / `float`              | `f64` / `f32`   |
| `int32` / `int64`               | `i32` / `i64`   |
| `uint32` / `uint64`             | `u32` / `u64`   |
| `bool`                          | `bool`          |
| `string`                        | `String`        |
| `bytes`                         | `ByteList`      |
| `repeated T`                    | `List<T>`       |
| `map<K, V>`                     | `TreeMap<K, V>` |
| a message                       | a `struct`      |
| a `oneof`                       | a `variant`     |
| `optional T`, explicit presence | `Option<T>`     |

A `map` is repeated key-value messages on the wire, and `TreeMap` iterating in
insertion order is what decodes into. A `oneof` is a set of fields of which at
most one is set, which is a `variant` whose cases carry the numbers.

A proto3 field with implicit presence has no `Option`. It decodes to its type's
default when absent, and it is omitted when it holds that default, which is what
the format says. Explicit presence is the `optional` keyword, and that is the
one that becomes `Option<T>`.

### Grog flattens what Wado cannot nest

A `.proto` nests messages and enums inside messages, and Wado has no nested type
declaration. Grog emits each as a top-level declaration named by joining the
path, and two that collide stop the build naming both. This is the rule Loam
already applies to ONNX tensor names.

A `reserved` range produces nothing. It says which numbers a future field may
not take, which is a rule about editing the schema rather than about the wire.

### The length prefix is a size pass

A `LEN` record writes its payload's length ahead of the payload, so an encoder
has to know how long a submessage is before it writes one. `core:protobuf`
answers that with a pass that computes sizes, followed by the pass that writes
bytes. The sizes travel between them in a list, pushed by the first pass and
read by the second in the same order, since both passes are the same derived
traversal. So no message needs a field to cache its own size in, which value
semantics would not have given it anyway.

The size pass is cheap in the way that matters. A `bytes` or `string` field's
length is known without reading it, so counting a hundred-megabyte tensor is one
addition. Only an integer costs anything to measure, and that is the width of
its varint. The pass is therefore proportional to the number of fields, while
only the writing pass is proportional to the bytes.

The alternatives are both proportional to bytes times nesting depth. Encoding
each submessage into a scratch buffer and copying it into its parent moves every
byte once per level above it. Writing into one buffer and inserting the length
afterwards shifts the payload once per level, unless the length is padded to a
fixed width, which the format parses but no other encoder produces. A deep
message holding a large leaf is exactly the shape that punishes both, and it is
the shape Loam reads: a tensor sits five levels down an ONNX model.

Two asserts keep the two passes honest. A submessage's written length is the
length its size pass promised, and the size list is empty when the message ends.
A traversal that disagreed with itself then traps rather than producing bytes
that decode as something else.

The cost is code size. A type serialized to protobuf has its `serialize` body
instantiated twice, once against each pass. Wasm size matters here and is not
what this decides on; speed is.

### No canonical encoding

`core:cbor` offers `to_bytes_canonical` because CBOR defines one. Protobuf does
not. The specification is explicit that serialization is not canonical across
implementations or versions, and map field order is unspecified, so bytes that
round-trip are not bytes that compare equal.

`core:protobuf` therefore offers no canonical form, and a signature over
protobuf bytes is a trap it declines to hand anyone. Encoding is deterministic
within this implementation: fields are written in declaration order. That is
what a build cache or a golden test needs, and it is not a claim about any
other encoder.

### The protobuf JSON mapping is a separate format

Protobuf defines a JSON projection with rules of its own for names, 64-bit
integers, and the well-known types. It is a different format that happens to
share a schema, so it belongs in a module of its own if it is ever wanted, not
in the wire codec.

## Roadmap

1. [x] `#[wire(number = N)]`. The attribute, the all-or-none check,
       `field_numbered`, `by_number`, and `WireNumbered`. A numbered struct
       serializes through `core:json` unchanged, and `serde_json_many_fields.wado`
       is byte-identical at `-Os` whether the derivation calls `field` or
       `field_numbered`. `by_number` has no test of its own, since `core:protobuf`
       is its first caller.
2. [x] `core:protobuf`. Varint, `fixed32`, `fixed64` and
       length-delimited; nested messages; repeated fields, written unpacked and
       read either way; a packed run reaching a field that is not repeated is its
       last element; a field the type does not declare is skipped. A
       hand-written message round-trips, and the encoder reproduces the byte
       sequences the specification's own worked examples give.
3. [x] Loam's ONNX subset. `package-loam/src/onnx_proto.wado` declares
       the messages Loam reads, with field numbers from `vendor/onnx/onnx/onnx.proto`
       — which declares them identically to `onnx-ml.proto`. Loam's Kiln generator
       takes a `.onnx` as readily as a `.onnxtext`, and `package-loam/conformance/`
       compiles graphs from the backend test data and reproduces the tensors ONNX
       ships beside them.
4. [ ] Grog's grammar. A `.proto` grammar in Gale, parsing proto3. Finished when the
       grammar parses the `.proto` files this repository has a use for, ONNX's
       included.
5. [ ] Grog's generator. The Kiln generator emitting declarations from the parsed
       schema. Its probe reports the whole file, since every byte of a `.proto` is
       schema. Finished when a `.proto` imported through Kiln produces messages that
       round-trip through `core:protobuf`.

## Known gaps

A repeated field is written unpacked, one tag per element, where proto3's
default for a repeated scalar is one packed `LEN` run. Both are legal and the
decoder reads either, so this costs bytes rather than interoperability. Packing
would have to be decided from the element type, which a serde sequence does not
name until its first element is written, and both passes would have to decide it
alike.

A repeated field's occurrences must arrive together. The decoder gathers a run
while the next tag repeats the same number, and an occurrence separated from the
rest by another field reaches the struct as a repeat of an already-filled slot,
where the last one wins and the earlier elements are dropped without an error.
Concatenating two encodings of one message is the format's defined merge and
produces exactly this, so it is not only an interleaving no encoder writes.

A zero-valued field is written rather than omitted. Proto3 says a field holding
its type's default is absent from the wire, so this implementation writes more
bytes than it has to, and a decoder of its output sees explicit zeros. The
inverse is what a declaration has to allow for: another encoder's output leaves
such a field out, so every field of a hand-written message needs a declared
default or decoding reports it missing.

A map and a `oneof` are both refused. `TreeMap` has no encoding here, and a
`variant` case with a payload has none either, since a case carries no
`#[wire(number = N)]` — the attribute reaches a struct field only.

Only the outermost message is checked for numbers. `WireNumbered` is a bound on
the entry points, and a field holding another message is not bound by anything,
so a submessage without numbers is reported when its bytes are produced rather
than where the call is written.

`int32`, `sint32` and `sfixed32` are one Wado type and three encodings. The
first is a varint, the second is zigzag, the third is fixed-width, and nothing
in `i32` says which. The 64-bit set has the same shape. A declaration that
cannot say which encoding a field uses cannot describe a schema that uses more
than one of them, and ONNX's does not, which is why this is not in the way of
the roadmap.

A `service` produces nothing. The grammar accepts one, since a real `.proto`
carries them and would not otherwise parse, and Grog emits nothing for it. So
the RPC interface a schema declares is invisible to a consumer, and a program
that talks to such a service writes the messages itself and the calls by hand.

A protobuf enum is open. An unknown value must survive a round-trip, and a Wado
`enum` is a closed set of cases with no case to put an unrecognized number in.

Unknown fields are dropped. Protobuf retains the fields a reader does not know
and writes them back out, which is what lets an old reader forward a new
message. Nothing in the serde data model holds them today.

proto2 is unread. Groups, extensions, required fields, and per-field defaults
are proto2's, and the mapping above is written against proto3. ONNX's canonical
schema is proto2 and this was not in Loam's way: `onnx.proto` uses no group and
no extension, and the rest of proto2 is proto3 on the wire, so the hand-written
declarations read it. A `.proto` Grog parses is another matter, since the
grammar has to accept what the syntax admits rather than what one file uses.

`Any` needs a descriptor at run time. It carries a type URL and bytes, so
decoding one means looking up a message by name, and every declaration here is
resolved at build time.

A user-written `T: FieldSchema` bound does not hold. The impl is synthesized
after elaboration, and only the derivations inside `core:serde` reach it, so a
program cannot ask a type for its field schema in its own words. This predates
the field number and is why `by_number` is pinned by its caller rather than
directly.

A `.proto` import is unresolved. `import "other.proto";` names a second file,
and a Kiln invocation names one primary with its inputs beside it, so which one
a Grog invocation reports in its extent and how a consumer spells the set is
undecided.
