# WEP: Kiln — Keyed IDL Lowering Notation

## Context

Wado is frequently expected to talk to schema-defined external systems: protocol
buffers, JSON-RPC, gRPC, GraphQL, OpenAPI, ORM definitions, ANTLR-style grammars,
WIT, WebIDL. For each of them, someone has to turn a schema into idiomatic Wado
source. Without a first-class mechanism, every such pipeline is wired by hand,
runs out of band, commits its output, and shares no contract, no cache, and no
story for users who want the same thing in their own projects.

Kiln (**K**eyed **I**DL **L**owering **N**otation) is that mechanism — the Wado
equivalent of Java annotation processors, Roslyn source generators, Swift macros,
or Dart's `build_runner`, narrowed to a single use case: **IDL → Wado source**.
The name joins Wado's element-themed tools (Tide for WebIDL, Gale for grammars)
as the fire in which raw schemas are fired into Wado source, and its expansion
names the four defining properties:

- Keyed — every invocation is content-addressed by a cache key covering schemas,
  options, and the generator's own source.
- IDL — the sole accepted input shape is an interface description language. Kiln
  is deliberately narrower than a build system.
- Lowering — schemas are lowered into plain Wado source that the ordinary
  compiler pipeline then handles with no further specialization.
- Notation — the surface is a declarative notation at the `use` site, not an
  imperative build script.

### Scope

In scope: registering generators, running them on schema files to emit `.wado`
source, and caching the result. Generators are ordinary Wado packages compiled to
Component Model components and executed under a sandbox; invocation is automatic
during `wado compile`.

Out of scope: in-compiler token-level macros (Rust `proc_macro`, Scala 3 quoted
macros); type-driven derive, which is
[trait derivation](./wep-2026-06-25-trait-derivation.md)'s concern; arbitrary
pre-build scripts à la `build.rs` — all code generation goes through the `kiln`
world and its sandbox; and compile-time file inclusion, which is
[`#include_str`](./wep-2026-03-02-include-str.md).

### Prior art

Languages with a serious IDL story land on one of four designs: in-compiler
plugins (Rust `proc_macro`, Roslyn, KSP — fast, but full host privilege),
out-of-process sandboxed plugins (Swift macros, protoc plugins — safer,
cacheable), arbitrary pre-build programs (`build.rs`, `build_runner` — flexible
but unsupervised), and manual on-demand generation (`go generate` — output
drifts). Wado's constraints point at the sandboxed-plugin design: generators are
Wado programs compiled to Wasm components, which is the execution model Wado
already speaks.

## Decision

### Design principles

1. Determinism by construction. The `kiln` world provides no clocks, randomness,
   network, environment variables, or ambient filesystem. A generator is a pure
   function `(inputs, options) → outputs + diagnostics`. Violating this would
   require rebuilding the compiler; it is not a runtime flag. This is the one
   guarantee in-compiler macro systems cannot cleanly make.
2. Every input is statically enumerable. No directory listing, no globs. Every
   file that feeds a generator appears as a literal path at a `use ... with`
   site, so the LSP can navigate to both the schema and the generated source and
   the compiler knows the full dependency graph before any generator runs.
3. Single-file scripts are first-class. Any generator configuration works inline
   at a `use` site, so a single `.wado` file with a shebang never needs a
   `wado.toml` just to consume a `.proto`.
4. Runtime-free compiler core. The compiler never links a Wasm runtime.
   Generator execution is a host capability on the same I/O boundary as source
   loading ([CompilerHost](./wep-2026-01-16-source-provider-abstraction.md)),
   because the compiler itself must keep building for
   `wasm32-unknown-unknown` — [the LSP](./wep-2026-04-18-lsp-architecture.md)
   ships it as Wasm.

### The generator contract

A generator is a Wado package that exports the `core:kiln/generator` world. The
compiler compiles it to a component and the host runs it; the returned files are
written out and re-enter the pipeline as ordinary Wado source.

What every generator shares is the host import and the exchanged types:

- `kiln-host` provides exactly two capabilities. `read-file` returns a UTF-8
  file resolved relative to the invocation's declaration site — it exists because
  real schemas have transitive references (`.proto` files importing `.proto`,
  GraphQL `extend type`, WIT `use`), and every call is recorded and folded into
  the cache key. `emit-diagnostic` reports a diagnostic that surfaces as an
  ordinary compile diagnostic, with an optional span into any file the generator
  knows about.
- `input-file`, `output-file`, `response`, and `error` are the value types
  crossing the boundary.

What is deliberately absent is as much of the contract as what is present. There
is no `write-file`: all outputs are returned in the response, which keeps the
generator a pure function of its inputs and caching a hash comparison. There is
no directory listing, no clocks, no randomness, no network, no sockets, no
environment. A generator that wants non-determinism would have to export a
different world, which the compiler refuses to load.

### Options are a typed argument in each generator's own world

Only `kiln-host` and the exchanged types are shared. The `generate` export is
not: a generator's options shape differs per generator, so each generator
synthesizes its own world whose `generate` takes the primary input, the
supplementary inputs, and its own options record as a third typed argument.

```wit
export generate: func(
    primary: input-file,
    inputs: list<input-file>,
    options: <the generator's own options record>,
) -> result<response, error>;
```

The options record is the generator's `pub struct Options` lowered by the
[Wado→WIT mapping](./wep-2026-01-29-wit-wado-mapping.md) — nested structs to
records, enums to WIT enums, `Option<T>` to `option<T>`, exact integer widths
preserved. There is no serialized blob, no schema document, and no introspection
export: options are just another typed CM boundary, so the compiler's existing
component-type and canonical-ABI machinery carries them. A generator that takes
no configuration omits the argument.

The cost of a per-generator signature is that the host invokes `generate`
dynamically rather than through a static binding. The shared imports and the
result shape are identical across generators, so only argument marshalling is
generic.

### Authoring a generator

A generator package names its entry file with the `generator` well-known-world
field in `[package]`, alongside `command` / `service` / `lib`. One package may
declare several, so the same package can be both a CLI and a generator.

```toml
[package]
name = "proto-codegen"
version = "1.2.0"
generator = "src/generator.wado"
command = "src/cli.wado"
```

The entry exports `generate` and, optionally, declares its options:

```wado
use { Request, Response, OutputFile, Error } from "core:kiln";

pub struct Options {
    namespace: String,
    emit_comments: bool = true,
}

export fn generate(req: Request<Options>) -> Result<Response, Error> {
    // ... parse `req.primary.content`, honour `req.options` ...
    return Result::Ok(Response {
        files: [OutputFile {
            path: `${req.options.namespace}.wado`,
            content: generated_source,
            is_entry: true,
        }],
    });
}
```

`Request<T>` is Wado-side sugar that bundles the three arguments; it never
crosses the boundary. It defaults to `Request<NoOptions>`, so a generator with no
configuration writes the bare `fn generate(req: Request)` and declares no
`Options` at all.

Option defaults follow the [Default trait](./wep-2026-03-04-default-trait.md)
design: omitting the whole `options` block means `Options::default()`, a field
with a default may be omitted individually, and a field without one must be
supplied. Because validation happens before the generator runs, typos and type
mismatches are reported at the `use` site and the LSP can complete option names
there.

Defaults are the one place where a source generator and a published one differ.
A generator resolved from source carries its per-field defaults; one resolved as
a prebuilt component has only its WIT, and a WIT record has no notion of a field
default, so every field is required at the use site unless its type is
`option<T>`. This asymmetry is accepted rather than closed: closing it would
require shipping defaults metadata beside the component, re-introducing the
self-description mechanism the typed-options design deliberately removed.

### Output layout

Every invocation emits exactly one entry module and zero or more supplementary
modules. The entry is what a `use { ... } from "<schema>"` binds to.
Supplementary modules are ordinary Wado files beside it, reached from the entry
by normal `use` statements with the usual visibility rules — Kiln defines no
virtual cross-file namespace, because once files are on disk they are just Wado.
Emitting zero entries, two entries, or a supplementary module with no entry is an
error reported against the generator's response.

The compiler stamps every generated file with a `#![generated(...)]` header
naming the generator and the schema paths that produced it:

```wado
#![generated(
    by = "example:proto-codegen@1.2",
    sources = ["./schemas/user.proto"],
)]
```

The header lets `wado format` and linters skip the file, lets the LSP offer "go
to schema", marks the file as derived for human readers, and gates collection of
stale outputs in the output directory. Unknown keys are tolerated so the header
can grow compatibly.

### Use-site syntax

A `use` clause whose source is a non-`.wado` path must carry a `with` clause that
fully specifies the invocation. A bare `use ... from "./schema.<ext>"` is an
error naming the missing clause.

```wado
#!/usr/bin/env wado run

use { User, Billing } from "./user.proto" with {
    generator: {
        module: "example:proto-codegen@1.2",
        options: { style: "rpc", emit_comments: true },
    },
};
```

The clause shape is fixed, and each field has a single type — there is no
string-or-record polymorphism to explain:

```
with {
    generator: {
        module: "<spec>",
        version?: "<semver-req>",
        registry?: "oci://<host>[/<prefix>]",
        options?: { ... },
        inputs?: ["<path>", ...],
        output_dir?: "<path>",
    },
}
```

- The literal after `from` is the primary schema; `inputs` lists supplementary
  schemas the generator cannot discover from the primary alone (a parser grammar
  assuming its lexer grammar, an OpenAPI spec with an external components file).
  Both must be `./` or `../` relative paths resolved against the declaring file,
  the same convention as a local module import. Files beyond these are picked up
  through `read-file` at generation time.
- `module` follows the same rules as any module specifier
  ([package and module syntax](./wep-2026-06-17-package-module-syntax.md)): a
  relative path compiles from source; a `[build-dependencies]` coordinate
  resolves against the manifest, compiling from source or pulling a prebuilt
  component depending on how that entry is declared. Bare names are rejected.
- `version` and `registry` supply a registry generator's source inline, for a
  single-file script with no `wado.toml` — principle 3. When the manifest does
  declare the specifier, the manifest is authoritative and inline forms are an
  error.
- `output_dir` redirects generated files off the default location; it is a
  relative path resolved against the declaring file. Files carrying
  `#![generated]` in that directory belong to the invocation and may be
  overwritten or removed by later runs; files without it are left alone and
  collide as an error.
- The `use` binds against the invocation's entry module, so imported symbols must
  be `pub` there. Go-to-definition on a symbol jumps to the generated file that
  defines it; go-to-definition on the `from` literal or an `inputs` entry jumps
  to the schema.

Two clauses that agree on generator, schema, inputs, options, and output
directory collapse into one invocation wherever they appear, so a project can
split imports of one schema across files without running the generator twice. Two
clauses that share a schema but disagree on any of those is a duplicate-generator
error naming both declarations. A second bare `use` against the same schema in
the same file rides the existing invocation.

### The loader redirect

A `use { Parser } from "./Calc.g4"` names a schema, not a module. The module the
user wants is whatever the generator emits, so at name resolution the compiler
rewrites that import to the invocation's entry module. Three properties follow,
and they are the reason the redirect exists rather than asking users to import
the generated file directly:

- Authors never hand-spell a generated filename. The generator owns its naming
  convention and can change it without touching consumers.
- The entry module need not exist before the first compile. On a fresh checkout
  the generators run first, and only then does name resolution look for it.
- Editor navigation lands on the schema or the generated file, never on a stale
  hand-written shim.

The redirect is scoped to the file that declared the `with` clause. An unrelated
file that imports the same schema with no clause of its own gets the
missing-clause error rather than being silently routed through someone else's
invocation. A `with` clause in an imported module still applies to that module's
own imports, so a generated module can be produced deep in a dependency tree.

### Build integration

Kiln runs between parsing and name resolution. Each `use ... with` clause becomes
an invocation; invocations form a DAG, since one generator may consume another's
output, and a cycle is an error. In dependency order, each invocation is either
served from cache or run, its outputs are written, and name resolution then
proceeds with the generated modules in place. Generated files go through the same
parser and elaborator as hand-written source, so a generator emitting invalid
Wado fails with an ordinary parse error against the file on disk.

Diagnostics reach files the compiler never parsed itself. A generator's span
names a path and a byte range; the compiler registers that file when it renders
the diagnostic, so a schema error is displayed with its snippet exactly like a
Wado error. A span into a file this run never read is shown without an excerpt.

Generators are declared in `wado.toml` under `[build-dependencies]`, which
accepts the same source shapes as `[dependencies]`, resolves in a separate
build-only graph, and locks separately. There is no manifest-side invocation
registry: every invocation is inline, so every file states which generator
processes which schema with which options.

### Caching

An invocation's cache key covers the resolved generator identity and its source,
the content of the primary and supplementary schemas, every file the generator
read on the previous successful run, the canonical form of the options value, and
the world protocol version. The compiled generator component is not part of the
key: its content is already determined by the generator source and the compiler
version, both captured elsewhere, and hashing it would force every generator to
re-run on a compiler upgrade for no added safety.

Cache state is recorded per invocation, in a file beside that invocation's
generated outputs — never in `wado.lock`, which stays dependency-pin-only.
Putting it next to the outputs is what makes the committed-source workflow work:
when the output directory is tracked, the cache file is committed with the
generated source, so a fresh checkout or a CI run hits the cache instead of
regenerating. Losing the cache file is never an error; the next compile rebuilds.

| Situation                                    | Behaviour                                                                   |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| No cache state                               | Run the generator; write outputs and cache state.                           |
| Key matches, outputs match what was recorded | Skip the generator.                                                         |
| Key matches, an output was edited by hand    | Skip the generator, warn, and honour the edit.                              |
| Key differs                                  | Run the generator; warn before overwriting a pre-existing differing output. |

Hand-edits are deliberately accommodated: tweaking a generated file to debug a
downstream problem should not mean fighting the build. The warning makes the
divergence visible without breaking the loop.

Two workflows fall out of `output_dir`. Left at its default, generated source and
cache state live under a gitignored build directory and a clean checkout
regenerates them. Pointed at a tracked directory, both are committed, so review
sees the generated source and web-based editors can navigate it.

### Consume-only mode

Any host that can run the compiler as Wasm can in principle run a generator — it
already has a Wasm runtime. In practice today's non-wasmtime hosts target older
WASI generations and do not support nested components, async, or WASI P3, which
is exactly the shape generators need. Until they do, such hosts run consume-only.

A consume-only host cannot run the generator, so it cannot re-derive any recorded
hash. Validating them would only make the redirect die and break every query over
a generated symbol, so consume-only trusts the artifact instead of verifying it:

- If the recorded entry output still exists within the workspace, it is loaded
  through the ordinary source path and compilation proceeds as if the user had
  written it, regardless of any drift since generation.
- Otherwise the compiler warns that no generated output was found and suggests
  compiling natively; the invocation's module is treated as unresolved, so
  imports of its symbols surface as ordinary resolution errors while the rest of
  the compilation proceeds.

Consume-only never writes. Freshness is `wado check`'s job, and consume-only
deliberately does not duplicate it, since it cannot run the generator to answer
the question.

Consume-only is a floor, not a ceiling: a host with a usable runtime runs
generators directly, which is what native `wado query` and the LSP backends
sharing its host do — so a query on a generated symbol resolves even on a fresh
tree with no prior compile, degrading to consume-only only if the pipeline fails.
It is a compatibility bridge, not part of the steady-state design; when web hosts
gain CM and WASI P3, nothing user-visible changes.

### `wado check`

`wado check` is the CI-facing companion to `wado compile`. It runs every
non-codegen phase, force-regenerates every invocation regardless of cache state,
byte-compares each fresh output against what is on disk, and promotes Kiln
warnings to errors. `--warn` opts out of the promotion for local triage.

The cache is deliberately ignored: the question is "would running the generator
now produce what is committed?", which is independent of any cache state, so the
answer is the same on a fresh clone and on a developer machine. Skipping Wasm
emission makes it meaningfully faster than a full compile. For projects that
leave `output_dir` at its default there is nothing committed to compare against,
so the check only verifies that every generator runs to completion.

### Versioning

The `kiln` world is versioned as an ordinary WIT interface. A generator declares
the version it targets; a mismatch against the compiler's supported set is a hard
error naming both sides. The world version is part of the cache key, so bumping
it invalidates every cached output automatically.

### Relationship to the existing pipelines

`wado-from-idl` stays a bootstrap tool: it generates the `wasi:*` standard
library Wado itself depends on, so authoring it in Wado would be circular. It
keeps its own out-of-band task and committed output.

[Gale](./wep-2026-03-02-gale.md) is first-party but self-hostable, and is driven
through Kiln: consumers write an inline `with` clause instead of running a
golden-file update task.

## Alternatives considered

### In-compiler macro system

Running generator code inside the compiler would be faster and drop the runtime
dependency, but it exposes the full host environment to every generator,
forfeiting determinism, and generators written in Wado could not participate
without a second mechanism. Reusing Wasm sandboxing keeps the plugin surface
consistent with the rest of the language.

### Linking a Wasm runtime into the compiler

The shortest path to a working prototype, rejected on two independent grounds.
The compiler must build for `wasm32-unknown-unknown`, which the runtime does not;
and the I/O boundary that already keeps source loading out of the compiler
applies equally to generator execution. A pure-Rust interpreter would keep the
compiler self-contained but none supports the Component Model, async, and WASI
P3 — the shape generators need.

### Out-of-band generation before compiling

A separate generate step would remove every runtime concern from the compiler,
but it breaks automatic invocation and kills the single-file script path. Host
delegation preserves both.

### Arbitrary pre-build programs

Maximally flexible and entirely unsupervised. Users who need it can run their own
shell before compiling; no language support is required.

### Globs and directory listing

Both hide the generator's input set from the LSP and from static tooling, and
introduce a "a file appeared in the directory" failure mode. An explicit path
costs one line per schema, paid once per project.

### A manifest-side invocation registry

Declaring invocations in `wado.toml` and letting bare `use` clauses pick them up
by matching paths reduces boilerplate, and was rejected for two failure modes.
A reader of a `.wado` file could not tell that an import was being processed by a
generator without consulting the manifest, so generator identity, options, and
even the existence of generation were invisible at the call site. And a manifest
entry was a project-wide rewrite hook: any file mentioning the same path was
silently routed through the generator, and clauses in different files could fight
over it. Inline-only restores both invariants. The cost is repetition in projects
with many schemas, accepted because the consuming surface is small and any
deduplication mechanism can be layered on later without breaking explicitness.

### Untyped options

Accepting options as an untyped blob would defer validation to generator runtime,
where errors are necessarily worse than the compiler's, and would cost the LSP
its completions at the `use` site.

## Open questions

- [ ] Enforce committed-source freshness in CI by running `wado check`.
- [ ] Watch mode. The caching design supports it; the command surface is
      unspecified.
- [ ] Parallel execution of independent invocations.
- [ ] A richer shape for the response error variant than
      `invalid-schema | unsupported | other`.
- [ ] The access scope of `read-file`. Any path the host accepts is served today;
      a stricter per-invocation allow-list may be worth revisiting.
- [ ] A project-root-relative escape hatch for paths at `use` sites.
- [ ] Web-host routing for generator execution, once a web host gains CM and
      WASI P3. Consume-only is the stopgap.
- [ ] Streaming or progress reporting from a running generator. Execution is
      blocking, so a long generator blocks the compile.
- [ ] A fuel or wall-clock budget for a generator run. There is no ceiling today;
      an early fixed default tripped on a large real grammar, so the knob likely
      belongs in the `with` clause, letting trusted local builds and untrusted CI
      pick different policies.

## Consequences

- Users gain a first-class way to consume any schema language that has, or can
  acquire, a Wado generator. Operationally this is close to Swift macros:
  sandboxed, deterministic, cacheable, automatic.
- `wado.toml` grows `[build-dependencies]` and a `generator` well-known-world
  field; `wado.lock` grows build-dependency pins only, with per-invocation cache
  state living next to the generated outputs.
- The compiler gains a phase between parsing and name resolution that plans
  invocations, compiles generators, delegates their execution, and materializes
  the output. The core stays I/O-free and runtime-free.
- Diagnostics extend to spans in files the compiler read on a generator's behalf;
  existing diagnostics are unaffected.
- Web editors start in consume-only mode. Projects that want a full experience
  there commit their generated source.
- Adding a new schema language becomes a matter of publishing a package that
  exports `core:kiln/generator`. No compiler change is required.
