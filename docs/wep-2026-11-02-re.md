# WEP: Re — Linear-Time Regular Expressions for Wado

## Context

Wado has no regular expressions. Code that needs one hand-writes a scanner, and
[WEP: Jade](./wep-2026-06-13-jade.md) lists the JSON Schema `pattern` keyword
as a known gap for want of an engine. JSON Schema defines `pattern` as an
ECMA-262 regular expression, so whatever Wado offers should read that syntax.

Compiling Rust's `regex` crate to Wasm and importing it as a component was the
first idea. It costs too much at the boundary. Each call lowers the subject
`String` into the other component's linear memory, and each match lifts its
offsets back. A regular expression is typically called many times on short
input, so this fixed cost dominates. The component also carries its own Unicode
tables, which dead-code elimination cannot reach. An engine written in Wado
reads the subject where it lies in the GC heap, returns a `StrSlice` over it,
and keeps only the code a program uses.

A backtracking engine, as in Perl, PCRE and every JavaScript engine, takes
exponential time on some patterns (ReDoS). A `wasi:http` service matching a
pattern against request data cannot afford that. RE2 and Rust's `regex` show
the alternative: give up the features that need backtracking, and match in time
linear in the input.

## Decision

### Re is a package

Re is `wado-lang:re`, in `package-re/`. Nothing of it is in the standard
library or the compiler.

Rust keeps `regex` out of `std`, and its reasons were weighed one by one:

| Rust's reason                                                                                             | For Wado                                                                    |
| --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `std` is stable forever, and `regex` 1.x still needed a rewrite of its internals (`regex-automata`, 2023) | Applies: the API and its semantics are not settled                          |
| The design space is wide: backtracking or linear time, Unicode by default or not                          | Settled here, by the sections below                                         |
| Cargo makes a crate as easy to reach as `std`                                                             | Applies: a package is one `[dependencies]` entry                            |
| The Unicode tables cost binary size and compile time                                                      | Does not apply: DCE removes what is unused, and `core:icu` holds the tables |

A package costs one thing: no module of the standard library can depend on it.
So Re moves to `core:re` once the standard library
itself needs a regular expression, or once its API settles. The move changes
only the import path.

### The syntax is ECMA-262's, in Unicode mode, without backtracking

A pattern is an ECMA-262 `Pattern` (§22.2.1), read as the `u` flag reads it.
That is the strict grammar, without the Annex B extensions, and it matches code
points rather than UTF-16 code units. The specification is the source of the
rules; no implementation is.

The pattern supports:

- alternation, groups, non-capturing groups and named groups `(?<name>…)`;
- greedy and lazy quantifiers, `{n,m}` included;
- character classes, `.`, `\d` `\w` `\s` and their negations, and `\b` `\B`;
- `\p{…}` and `\P{…}`, with the property data from `core:icu`;
- the anchors `^` and `$`;
- the modifiers `(?ims-ims:…)` of ES2025, which scope `i`, `m` and `s` to a
  group. They are how a pattern sets a flag, since a tag takes no flag
  argument.

`\p{…}` reads its properties from `core:icu`, at the Unicode version
`core:icu` carries, and accepts every property and value it knows. So it may
accept a name ECMA-262's tables do not list, and a character may have a
property here that it lacks in a JavaScript engine of another Unicode version.
Re does not narrow `core:icu` to match ECMA-262 or any engine. A conformance
test that turns on the Unicode version is measured against `core:icu`'s data.

Backreferences (`\1`, `\k<name>`) and lookaround (`(?=` `(?!` `(?<=` `(?<!`)
are rejected. No linear-time engine can run them. The error names the construct
and says so, instead of reporting a syntax error.

Groups nest at most 256 deep, as Rust's `regex` bounds its nesting, so a
pattern read at run time cannot exhaust the stack.

Every other rule follows ECMA-262, the surprising ones included. `\d` is ASCII,
and so are `\w` and `\b` except under `i`. Under `i`, two characters match when
their simple case foldings are equal (`Canonicalize`, §22.2.2.7.3), so `\w` also
matches U+017F and U+212A, which fold to `s` and `k`, and `\b` counts them as
word characters (`WordCharacters`, §22.2.2.9.4). `.` and the `m`-mode anchors treat
`\n`, `\r`, U+2028 and U+2029 as line terminators. When alternatives compete,
the leftmost match wins, and within it the priority ECMA-262 gives the
alternatives and quantifiers. This is the leftmost-first rule that Perl and
JavaScript share, not POSIX's leftmost-longest.

### Matching takes linear time

A match takes O(m × n) time for a pattern of size m and an input of n bytes,
for every pattern and every input. A Pike VM, simulating the NFA one input
position at a time, guarantees this and reports captures. A lazy DFA, built
state by state as the input reaches it, answers `is_match` and the bounds of a
match faster, and the Pike VM then runs only over the span the DFA found.

The tree a pattern parses to holds code points, since ECMA-262 states its rules
over them. Compiling it turns each character class into the UTF-8 byte
sequences of its code points, so both engines step over the text's bytes and
decode nothing. A DFA's transition table is 256 entries wide, a literal
prefilter searches bytes, and an offset needs no conversion. An assertion
(`\b`, `^` and `$` under `m`) decodes the characters around its position, and
only there.

### The text is UTF-8, and offsets are bytes

The subject is any `AsStrSlice`, and a match is a `StrSlice` over it, so
neither copies. Offsets count bytes, as every offset in a Wado string does.
This departs from ECMA-262's UTF-16 indices (`lastIndex`, `match.index`), which
only a JavaScript host would want.

A pattern may still name a lone surrogate (`\uD800`), as ECMA-262 allows. No
UTF-8 text holds one, so that atom never matches.

### Two tags, `re` and `rex`, and a constructor

`re` takes the pattern as written. `rex` is Perl's `/x`: outside a character
class, whitespace (Pattern_White_Space, the set Perl ignores) is ignored and `#` starts a comment that runs to the end of
the line. A literal space or `#` is written in a class (`[ ]`, `[#]`) or
escaped (`\ `, `\#`). The other escapes mean what they mean in `re`. `rex` is
the only place Re extends ECMA-262.

Both tags read the template's text (`lit(&t)`), and a pattern is written as a
[raw template](./spec-literals.md#raw-template-strings), ``re#`…`#``, so each
backslash reaches the pattern as written. In a cooked template the lexer reads
the escapes first: `\d` is an error there, and `\b` a backspace.

`Regex::new(pattern)` builds a regular expression at run time and reports a
malformed pattern as an `Err`. The tags build theirs the same way and panic on
one, since a literal pattern that does not parse is a bug in the program.

```wado
use { re, rex, Regex } from "lib:re";

global DATE: Regex = re#`(?<y>\d{4})-(?<m>\d{2})-(?<d>\d{2})`#;

global FLOAT: Regex = rex#`
    ^ [+-]?
    ( \d+ (\.\d*)? | \.\d+ )   # mantissa
    ( [eE] [+-]? \d+ )?        # exponent
    $
`#;

let user_pattern = Regex::new(input)?;
```

A `global` builds its regular expression once, on first read.

### Raw literals

A cooked template rejects an escape the lexer does not know, so `` re`\d+` `` is
an error (`invalid escape sequence: \d`), and so is `` `C:\Users` ``.
Raw literals were added to the language for this, in two forms. A raw template,
``#`…`#``, takes every backslash as itself, and a hole still opens at `${`. A
raw string, `#"…"#`, opens no hole, so a pattern assembled at run time is
written without escaping a `$`: ``Regex::new(`${prefix}${#"\d+$"#}`)``. A
raw byte string, `b#"…"#`, completes the set. The lexer keeps each literal's
text as written along with its `#` count, and decoding it to a value reads the
count: a raw literal's value is its text. A tag reads a raw template like any
template, with `raw(&t)` equal to `lit(&t)`, and the formatter prints the text
it was given.

The delimiter is `#` with no prefix, as in Swift. `` #` `` and `#"` were syntax
errors before, and Wado has no macros, so no existing token sequence changes
meaning, which is what Rust's `r` prefix guards. The closer repeats the
opener's `#` count, which `Wado.g4` keeps on a lexer member and checks in a
predicate, so the grammar Gale builds lexes the same counts the compiler does.

Two other designs were weighed and refused. An attribute marking a tag that
reads only raw text, which the tagged-template WEP rules out (no marker, no
inspection of the tag). And a check deferred until the tag reads the cooked
text, which would make whether a literal lexes depend on the tag's body.

### A hole is a literal, unless it is a `Regex`

A hole holding text matches that text literally, as if it went through Perl's
`\Q…\E`. A hole holding a `Regex` is spliced in as a non-capturing group. Its
own groups keep capturing, numbered by where their opening parentheses fall in
the combined pattern. A hole's type implements `PatternPart`, which Re
implements for `String`, `StrSlice`, `char` and `Regex`.

Two groups in the combined pattern may not share a name, whichever parts they
came from, as ECMA-262 rejects two in one pattern. The tag panics on such a
pair, naming the group, like any other malformed pattern.

```wado
let word = re#`\w+`#;
let greeting = re#`^${prefix}: ${word}$`#;   // `prefix` matches as plain text
```

Perl interpolates text as pattern syntax. Re does not, so that text from a user
cannot inject syntax. A program that means to build a pattern from text says
so with `Regex::new`.

A template with holes builds a new regular expression each time it is
evaluated. Only a hole-less template is constant.

### The API

```wado
impl Regex {
    pub fn new<S: AsStrSlice>(pattern: S) -> Result<Regex, PatternError>;
    pub fn is_match<S: AsStrSlice>(&self, text: S) -> bool;
    pub fn find<S: AsStrSlice>(&self, text: S) -> Option<Match>;
    pub fn find_at<S: AsStrSlice>(&self, text: S, start: i32) -> Option<Match>;
    pub fn find_iter<S: AsStrSlice>(&self, text: S) -> Matches;
    pub fn captures<S: AsStrSlice>(&self, text: S) -> Option<Captures>;
    pub fn captures_at<S: AsStrSlice>(&self, text: S, start: i32) -> Option<Captures>;
    pub fn captures_iter<S: AsStrSlice>(&self, text: S) -> CaptureMatches;
    pub fn replace<S: AsStrSlice, R: Replacer>(&self, text: S, with: R) -> String;
    pub fn replace_all<S: AsStrSlice, R: Replacer>(&self, text: S, with: R) -> String;
    pub fn split<S: AsStrSlice>(&self, text: S) -> Split;
}
```

A `Match` answers `start()`, `end()` and `as_str()`. `Captures` is indexed by
number (`caps[1]`) and by name (`caps["y"]`), each an `Option<Match>`. An
iterator that finds an empty match moves past the next character before it
searches again, as `String.prototype.matchAll` does.

`find_at` and `captures_at` search from the byte offset `start`, which must lie
on a character boundary. The text before it still counts as context, so `^`
matches only where it would in the whole text, and `\b` reads the character
before `start`. A loop that resumes where each non-empty match
ended finds what `find_iter` finds.

`Replacer` is what `replace` writes in place of each match. Re implements it for
a `String` or `StrSlice`, which reads `$1`, `$<name>`, `$&` and `$$` as
ECMA-262's `GetSubstitution` does, and for `fn(&Captures) -> String`, whose
result is inserted as it is.

### No Kiln generator

A Kiln generator could lower a pattern to Wado code at build time. It is not
offered. It would need the pattern in a file of its own, and it could not build
a pattern at run time, so it would be a second API beside the one above.

Compiling a constant pattern ahead of time is the compiler's job instead.
`re` is a pure function, so a hole-less ``re#`…`#`` is a call with constant
arguments. `niri` can fold that call
([WEP: NIR Interpreter](./wep-2026-04-27-nir-interpreter.md)), and the
automaton it produces can become a constant global
([WEP: Constant Object Globalization](./wep-2026-05-31-const-object-globalization.md)).
A pattern that does not fold is a missed optimization in the compiler, not a
reason to change Re.

## Roadmap

- [x] Raw literals, ``#`…`#``, `#"…"#` and `b#"…"#`: the compiler's lexer,
  the formatter, the TextMate grammar and `Wado.g4`, with the rules in
  `spec-literals.md`.
- [x] Vendor the ECMA-262 specification (`tc39/ecma262`) and test262's RegExp
  tests under `vendor/`. The parser's rules cite the first, and the second
  is the conformance corpus.
- [x] The parser: a `Pattern` to an AST, `rex`'s whitespace and comments,
  errors that point at the offending character, and the errors that name
  a rejected backreference or lookaround.
- [ ] The Pike VM, behind the whole API. A differential test runs each pattern
  through Node's `RegExp` with the `u` flag, a black-box oracle, and maps
  its UTF-16 indices to byte offsets.
- [ ] Jade's `pattern` keyword matches with Re, which closes that known gap.
- [ ] The lazy DFA, behind `is_match` and `find`, with the Pike VM confined to
  the span the DFA found. A fuel benchmark measures the gain.
- [ ] A literal prefilter on `core:simd`, which skips to where a pattern's
  required literal occurs.

## Known gaps

- The `v` flag's syntax: set operations in a class (`[\p{L}--[a-z]]`) and
  string properties.
- Lookaround and backreferences, even in the forms that linear time could
  admit.
- A malformed literal pattern panics when the program runs, not when it
  compiles.
- `core:icu` folds whole strings with full case folding. ECMA-262's `i` needs
  the simple folding of one character, which `core:icu` does not offer yet.
- No offsets in UTF-16 code units for a host that speaks JavaScript.
- A whole-pattern flag `(?i)` at the start of a pattern. ECMA-262 has only the
  scoped form.
- Duplicate group names in different alternatives (ES2025).
- Matching bytes: no `Regex` searches a `ByteList` or text that is not UTF-8.
- A match anchored at a given offset, as ECMA-262's `y` flag gives: `find_at`
  finds the leftmost match at or after `start`.
- A `Replacer` closure that performs effects.
- A repetition count above 4294967295, which ECMA-262 accepts.
