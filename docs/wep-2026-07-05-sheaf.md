# Sheaf & Marl — A Minimal Blog System

## Context

The Wado project needs a blog at `wado-lang.github.io`. Rather than reach for
an existing generator, we build one in Wado and compile it with Wado's own
toolchain — the blog becomes a dogfooding vehicle for the language, the
package system, and the WASI filesystem bindings.

The design goal is stated up front: start small, grow big. The minimal system
must be genuinely small (few moving parts, no persistence, no server) yet leave
clean seams for later growth (feeds, taxonomies, richer Markdown).

### Prior art

Minimal blog systems fall into a few lineages, distinguished by what each
treats as the irreducible core:

- Data-model-first (Rails' 2005 blog demo): the `Post`/`Comment` CRUD is the
  core; everything else layers on. Requires persistence.
- Read/write boundary (Flask `flaskr`): even a minimal blog has an
  authenticated author boundary over a public read view.
- Pure function (Jekyll, Hugo, Zola): a blog is a deterministic transform from
  content files to a site. No runtime, no database.
- Constraint-as-philosophy (Bear Blog): minimalism as a product value —
  Markdown in, fast static HTML out, no client JS.
- Extension seam (WordPress, Ghost): what let them grow — hooks, or a clean API
  boundary — is also what determined their long-term shape.
- Variable post shape (tumblelog, microblog): even "what is a Post" is a
  choice, not a given.

The central fork is static generator (CLI, pure transform) versus dynamic
service (`wasi:http/service`, needs storage and auth). Because the target is
GitHub Pages — static hosting at the organization root — we take the pure
function model. It is also the model that maps most directly onto Wado's value
semantics and deterministic Wasm output, and it needs no persistence, which
sidesteps the absence of a `wasi:keyvalue` binding today.

### Current capabilities and gaps

Available: `wasi:filesystem` (directory walk, streamed read/write),
`core:temporal` (post dates), `core:json` (front matter), `core:url`, and the
language's own template string literals (HTML templating).

Missing, and therefore built here: a Markdown-to-HTML processor, and an HTML
escaping helper. The Markdown processor is the substantive piece of work and
gets its own package.

## Decision

Ship two packages: `Marl`, a Markdown-to-HTML processor, and `Sheaf`, the
static blog generator that consumes it. Both are `package-*` workspace members
(not stdlib), mirroring `package-gale`.

### Names

The ecosystem's tool names are short, evocative natural nouns — Gale (Grammar
Adaptive LL Engine), Tide (the WebIDL binding generator), Kiln (Keyed IDL
Lowering Notation). Read as elements, they cover air, water, and fire.

Marl — Markdown Adaptive Rendering Layer. Marl is a calcareous earth (a
mudstone), completing the elemental set with earth, and its spelling echoes
"Markdown".

Sheaf — Static HTML Engine And Feed. A sheaf is a bound bundle of gathered
grain; the generator binds individual posts into a published collection. The
mathematical sense — gluing local sections into a global object — mirrors the
transform from per-post content (local) to a whole site (global).

- `package-marl/`, module id `wado:marl@0.1`
- `package-sheaf/`, module id `wado:sheaf@0.1`

### Architecture: a pure static transform

Sheaf is a CLI program (`wasi:cli/command`). It reads a content directory,
renders each post, and writes a site directory. No database, no server, no
persistence between runs.

```
content/*.md ──► split front matter ──► Marl.render(body) ──► apply template ──► _site/
                 (---json)               (Markdown → HTML)     (template literal)
```

Filesystem I/O is the only effect. The rendering core (front matter split,
Markdown, templating) is pure and unit-testable without WASI.

### Marl: the Markdown processor

Marl renders a GFM subset. It has no I/O — a single pure entry point over
strings, which keeps it trivially testable and reusable outside Sheaf.

```wado
// package-marl/src/marl.wado
pub fn render(source: &String) -> String { ... }
```

Supported blocks (v0.1):

| Block          | Notation                               |
| -------------- | -------------------------------------- |
| ATX heading    | `#` … `######`                         |
| Paragraph      |                                        |
| Fenced code    | `` ``` `` / `~~~`, with language label |
| List           | `-` / `1.`, nestable                   |
| Blockquote     | `>`                                    |
| Thematic break | `---` / `***`                          |
| Table (GFM)    | `\| a \| b \|`                         |

Supported inline (v0.1): emphasis (`*em*`) and strong (`**strong**`), inline
code (`` `code` ``), links (`[text](url)`), images (`![alt](url)`),
strikethrough (`~~del~~`), autolinks (bare URLs), and hard line breaks.

Fence rules follow CommonMark: an opening fence is three or more of the same
character (`` ` `` or `~`); the closing fence uses the same character and is at
least as long as the opening one. This lets a code block that itself contains a
triple-backtick fence be wrapped in a longer fence — useful for a compiler
blog that shows Markdown and shell snippets.

HTML safety: `<`, `>`, `&`, and `"` in source text are always escaped. Raw HTML
passthrough is not supported — HTML in the source is rendered as literal text.
This keeps the renderer simple and the output safe by construction.

Deliberately out of scope in v0.1 (each a later growth line): setext headings,
reference-style links, indented (non-fenced) code blocks, GFM task lists, raw
HTML passthrough, and every extension beyond GFM (footnotes, callouts, heading
anchors, math).

### Front matter: fenced JSON

Each post opens with a JSON front matter block fenced by a language-tagged
delimiter:

```
---json
{ "title": "Effect handlers", "date": "2026-07-05", "index": true }
---
```

This is the gray-matter / Eleventy convention (`---json`), chosen over Hugo's
brace-delimited JSON because the `---` fence stays visually constant while the
language tag names the parser. It reuses `core:json`, so no new parser is
needed. The tag is the growth seam: a future `---yaml` or `---toml` slots into
the same framework once those parsers exist, and the default format can move to
YAML later without breaking existing posts.

```wado
// package-sheaf/src/front_matter.wado
pub struct FrontMatter {
    pub title: String,
    pub date: String,               // ISO 8601, parsed via core:temporal
    pub tags: List<String> = [],    // parsed but unused in the MVP
    pub index: bool = true,
}

impl Deserialize for FrontMatter;
```

### Sheaf: the blog generator

The Post model is intentionally small:

```wado
// package-sheaf/src/post.wado
pub struct Post {
    pub title: String,
    pub date: ZonedDateTime,   // core:temporal; drives ordering
    pub slug: String,          // derived from the file name
    pub body_html: String,     // produced by Marl.render
    pub index: bool,
}
```

The `index` flag is the whole draft mechanism. One boolean, whose name states
its behavior literally — it controls whether a post appears in both indexes:

- the site index page (the post list), and
- the search index (via a `robots` meta tag).

When `index` is absent it defaults to `true` (a normal published post). When
`index: false`:

1. the post is omitted from the index page;
2. its individual page is still generated (reachable by direct URL, so it works
   as a shareable preview);
3. that page carries `<meta name="robots" content="noindex, nofollow">`.

Because the repository is public, the Markdown source is public regardless;
`index: false` is therefore an "unlisted" state, not a secret one. That is the
right minimal semantics for a public-repo blog, and folding listing and
indexing into a single well-named flag makes the coupling principled rather
than incidental. Splitting the two concerns, a truly ungenerated draft, a
`--drafts` local preview build, and a `robots.txt` are all growth lines.

Outputs (MVP): the index page listing published posts newest-first, and one
page per post. Feeds (RSS/Atom), tag pages, and pagination are explicitly the
next step, not the first.

Templating uses the language's own template string literals plus a small HTML
escaping helper; no separate template engine. (A JSX-style templating language
is a longer-term language direction, out of scope here.)

CLI:

```sh
sheaf build                          # content/ → _site/
sheaf build -i content -o _site      # explicit input/output directories
```

### Project structure

```
package-marl/
  wado.toml
  src/
    marl.wado          ← pub fn render(source) -> String
    lexer.wado         ← block/inline scanning
    inline.wado        ← inline rendering + HTML escape
    html.wado          ← escaping helpers
    *_test.wado

package-sheaf/
  wado.toml
  src/
    main.wado          ← CLI entry (`sheaf build`)
    front_matter.wado  ← ---json split + FrontMatter
    post.wado          ← Post model, slug derivation
    site.wado          ← index + per-post generation
    template.wado      ← HTML templates (template literals)
    *_test.wado
```

`package-marl/wado.toml`:

```toml
[package]
name = "marl"
description = "A GFM-subset Markdown-to-HTML renderer written in Wado"
repository-directory = "package-marl"
```

`package-sheaf/wado.toml`:

```toml
[package]
name = "sheaf"
description = "A minimal static blog generator written in Wado"
repository-directory = "package-sheaf"

[world]
"wasi:cli/command" = "src/main.wado"

[dependencies]
marl = "0.1"
```

Sheaf imports Marl as an ordinary package:

```wado
use { render } from "wado:marl@0.1";
```

Both packages join `[workspace].members` in the root `wado.toml`.

### Deployment

A GitHub Actions workflow builds the site with the Wado toolchain and deploys
`_site/` to Pages. Because `wado-lang.github.io` is an organization page, the
site is served from the root, so no path-prefix handling is needed.

```yaml
# .github/workflows/blog.yml (sketch)
# build: run `sheaf build` (compiled to Wasm, executed with wasmtime)
#        over content/ to produce _site/
# deploy: actions/deploy-pages with _site/ as the artifact
```

## Consequences

### Positive

- The blog is built by Wado's own compiler and packages — real dogfooding of
  the package system, `wasi:filesystem`, `core:temporal`, and template strings.
- Marl is a self-contained, I/O-free package, independently useful and testable.
- No persistence and no server: the whole system is a deterministic transform,
  matching Wado's value semantics and static hosting on Pages.
- `Sheaf` and `Marl` extend the ecosystem's naming scheme and complete its
  elemental set.
- Every deferred feature (feeds, tags, YAML front matter, wider Markdown) has a
  named, non-disruptive growth seam.

### Negative

- A hand-written Markdown parser is real work, and a GFM subset will diverge
  from full CommonMark in edge cases until coverage grows.
- `index: false` is unlisted, not private; drafts are publicly reachable by URL.
  Acceptable for a public repository, but must be documented so it is not
  mistaken for access control.
- No incremental build in the MVP: every run regenerates the whole site.

### Trade-offs

Static generation over a dynamic service: a `wado serve` blog would exercise
the HTTP world, effects, and async, but demands storage and auth on day one.
Static generation is the smaller, Pages-compatible starting point; a dynamic
front end over the same content model remains a later option.

Fenced JSON front matter over YAML: YAML is friendlier to hand-author, but a
YAML parser exceeds the minimal scope. Fenced JSON reuses `core:json` today and
leaves `---yaml` as a drop-in growth line.

A single `index` flag over separate listing/indexing controls: coupling is
simpler and, given the name, self-explanatory; the concerns can be split later
if a real need appears.

A hand-written parser over Gale: Marl does not use the `Gale` parser generator,
because Markdown is not context-free. The CommonMark fence rule (a closing
fence at least as long as the opening one) is context-sensitive and cannot be
expressed in a context-free grammar; block structure is defined as a line-based
stack machine with lazy continuation, and emphasis resolution uses a delimiter
stack with backtracking. These defeat an ANTLR-style LL grammar, which is why
every serious Markdown implementation is hand-written. Gale remains the right
tool for context-free DSLs, not for Markdown.
