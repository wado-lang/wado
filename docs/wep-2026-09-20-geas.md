# WEP: Geas — Tensor Compilation for Wado

## Context

Wado has no tensor story. The closest thing in the tree is
`example/microgpt.wado`, a scalar autograd graph where every arithmetic
operation allocates a `Value` node. It is a faithful port and a useful GC
benchmark. It is not a foundation for machine learning work.

What Geas is for is inference on the device: a browser, a phone, an edge
worker. Those places share three constraints that a datacenter never has. Every
byte of the module is downloaded before the first token, so the module must
carry only what the model uses. The process starts cold, often per request, so
there is no warmup to amortize a JIT against. And a GPU is a possibility rather
than a given, so the CPU path is a production path. An engine that ships an
interpreter and the graph as data pays all three; a module compiled from the
graph ahead of time pays none of them, and that is the shape Geas takes.

Four findings from the 2026 literature drive this proposal.
`docs/research-ml-inference-webgpu.md` records the survey they come from.

Compile-time shape checking has become implementable. Dependent and refinement
types both demand proofs to decide type equality, which is why neither was
adopted in practice. Staging replaces the proofs with assertions evaluated as
compile-time computations, and the ECOOP 2026 work validated it on ported
ocaml-torch programs.

Axis notation has converged on einx, whose bracket marks the axes an operation
actually sees. Static checking of it exists only as external stubs, because
Python cannot say in a type what an operation does to a shape. That is a
constraint of the host language rather than of the idea, and it is the reason
this design has no notation layer at all.

Quantization formats are a moving target parameterized by block size, scale
representation, and rotation, not a fixed list of names.

Fusion's objective function is not what it was. On WebGPU at batch size 1,
dispatch count dominates and kernel quality does not. That objective belongs to
the GPU work, and naming it here is what bounds the claims a CPU MVP can make.

Gale is the architectural precedent, and a measured one. Its generated parser
beats hand-written `sqlparser-rs` by 1.12x and tree-sitter's native Rust by
2.19x. Its architecture is a static compiled fast path with escalation to a
runtime tier. This WEP adopts five properties of it:

- The escalation boundary is a decidability result. Gale escalates because the
  lookahead language of a recursive ambiguous prefix is non-regular, so subset
  construction provably does not converge.
- The escalation sites are enumerable and named. Gale's simulator decides
  exactly three parser sites, each pinned by a fixture and visible through
  `gale dump --atn`.
- Cost routes as much as correctness does. Two sites that belong on the
  simulator for correctness stay static because measurement showed 2.6 ms
  becoming 402 ms, and the divergence is pinned rather than hidden.
- An unused mechanism costs nothing. A grammar needing no simulator carries
  none and is byte-for-byte unaffected.
- The runtime is inlined into the generated file, which is what removes
  version drift between generator and runtime.

Version drift is a problem the field has not solved. ONNX opset drift and
checkpoint incompatibility are both drift between a model artifact and the code
that runs it, which is what the last property removes.

Kiln makes the staging available without a language change. Wado has neither
const generics nor general compile-time evaluation, so an extent cannot be
carried as an integer in type position. A Kiln generator, however, runs
arbitrary Wado at compile time and emits Wado source, which is staging. Gale
already works this way. Geas is therefore a package, not a language feature.

## Decision

### Name

Geas — in Irish myth, a binding laid on someone that cannot be broken.

The name states the bargain this design makes. A geas is accepted rather than
suffered, and what it buys is power. A model that submits to fixed shapes at
build time gets fused kernels, and gets its shape errors at build time instead
of wrong numbers at run time. The constraint is the mechanism, not a limit on
it.

A short concrete noun, consistent with Gale, Kiln, Jade, and Marl. It leaves
those names' elemental theme, which is already fully occupied.

### A Kiln Generator, Not a Library

Geas is invoked as a Kiln generator over a model graph and its checkpoint:

```wado
use { Model } from "./model.onnxtext" with {
    generator: {
        module: "wado-lang:geas@0.1",
        inputs: ["./model.safetensors"],
    },
};
```

A library would place shape checking at run time, where every other framework
already has it. Only a generator can place it early enough for a shape mismatch
to stop the build.

Three properties follow from the choice, and each answers a standing problem in
the field:

- A Kiln generator runs in a full Wasm sandbox. A build-time code generator that
  reads untrusted model files is an obvious attack surface, and both `build.rs`
  and `setup.py` execute with the developer's privileges. Geas cannot.
- The generated module carries its own kernel runtime, inlined as Gale's is.
  There is no separate runtime package to version-match, so opset drift has no
  place to occur.
- The generated module is ordinary Wado. It is readable, debuggable, and
  optimized by the same pipeline as any other Wado source.

### The Graph Is ONNX

A forward pass is read rather than written. Geas takes a model graph in a
language the field already has, and the first one is ONNX, with StableHLO to
follow as a second front end.

The operators mean what ONNX says they mean: broadcasting, each operator's
definition, and the opset version that fixes it. Geas declares the opset range
it reads and reinvents none of it. This is where most of the robustness comes
from. A graph language of Geas's own would have had semantics of Geas's own, and
every rule of them would have been Geas's to specify, to test, and to get wrong.
ONNX's rules come with a reference implementation and a conformance suite, and
that suite is the oracle the kernels are tested against.

The syntax is ONNX's textual format, the one `onnx.parser` reads and
`onnx.printer` writes, in a file named `.onnxtext` as onnx-mlir names it. A Gale
grammar parses it. The protobuf form is a gap, since the tree has no protobuf
reader; a model exported as protobuf is converted to text outside the build,
which is one call to `onnx.printer`. A textual graph is a few kilobytes, so a
test fixture is written by hand, and the two-layer MLP of roadmap step 1 is one.

The graph names its weights and the checkpoint supplies them. An initializer's
name is the key into the checkpoint, which is what lets the graph be the `from`
literal and the checkpoint an `inputs` entry. A sharded checkpoint is several
entries.

An ONNX shape is positional, with a `dim_param` where a dimension is symbolic.
That is the extent half of an axis and none of the identity half, so the axis
schema of the next section names the axes of the graph's inputs and
initializers, and the shape algebra carries those names and extents through
every operator by its ONNX signature. An intermediate value is never named by
hand. A `dim_param` is a symbolic extent; a `dim_value` is a static one.

This settles who Geas is for. A graph reaching it has already run once, in the
framework that exported it, so its shapes are consistent by construction. What
the build catches is the seam that framework never saw: a checkpoint whose
extents disagree with the graph, and a caller whose tensors disagree with the
boundary.

### The Graph Is the Schema, the Checkpoint Is Data

The graph is the schema, and the generated code is a function of it. A
checkpoint carries data, behind a header of its own: a safetensors header is a
length-prefixed JSON blob at the front of the file carrying tensor names,
positional shapes, dtypes, and offsets. The build checks that header against the
graph and reads nothing further down the file.

Kiln's probe is what makes that pay. A generator reports how many leading bytes
determine its output, and the build keys on that range; the mechanism and the
two invariants a probe owes are in the Kiln WEP. Geas's probe reads a
safetensors header, which satisfies both. The header length is in the first
eight bytes, so the extent is determined by bytes inside it.

Without it the build would hash whole checkpoints. Hashing measures about
2 GB/s here, so that is seconds on every incremental build, spent proving that
bytes the output never depended on did not change.

The graph file is probed too, and its extent is the whole file, since every byte
of a textual graph is schema. An extent is a prefix, so a format that
interleaves its schema with its data has none, and this is what a protobuf
`.onnx` does: graph and initializers in one message, interleaved, so no prefix
excludes the weights. When the protobuf form arrives, a model must keep its
weights in external data files, which is
`onnx.save_model(..., save_as_external_data=True)` and is what every model over
2 GB already does, since protobuf caps a message there. A stated input
requirement is what keeps the extent a length instead of a range set; the
alternative was generalizing the extent so one input could name several disjoint
ranges, which complicates the key, the record, and every generator that never
needed it.

Geas is the reason Kiln's probe receives the invocation's options:
`inline_weights` makes the output depend on the whole file rather than on the
header, so a probe blind to it would either report the whole file every time,
losing what the extent was for, or report the header and let a payload-only
change hit the cache and emit a module carrying the old weights.

Per-input probing is what a real checkpoint needs. Large models ship sharded —
`model-00001-of-00003.safetensors` beside an index — so several huge inputs
arrive at one invocation, each with a header of its own.

The generated module contains the typed graph, the kernels, and a loader that
checks the incoming payloads against the shapes the header declared. A
checkpoint that does not match its header reports which axis disagreed, at load
time, rather than producing wrong numbers.

A small model may set `inline_weights` to have the payload emitted as
`#include_bytes`, which makes the component self-contained. This is for test
fixtures and very small models, not the normal path.

### Axis Identity Is a Type, Extents Are Values

An axis has a name rather than a position. Transposition is then a change of
description rather than a movement of data, and an operation states which axes
it consumes.

An axis is a marker type, and a tensor carries its axis list as one type
parameter: `Tensor<f32, [Batch, Seq]>`. Naming the same axis variable twice in
a signature makes the two positions agree, so a contraction checks itself:

```wado
fn matmul<M, K, N>(a: &Tensor<f32, [M, K]>, b: &Tensor<f32, [K, N]>) -> Tensor<f32, [M, N]>
```

`example/tensor_axes.wado` is the working form, with a forward pass built on it.
Rank-generic operations take the axis list as a plain type parameter, and an
operation that changes the rank destructures it with a pack, so a reduction is
`<..Rest, Last>(t: &Tensor<f32, [..Rest, Last]>) -> Tensor<f32, [..Rest]>`.

This needs no language change. It was the open question when this WEP was
written, because Wado has no const generics, and it is closed: an extent cannot
be carried in a type, but an axis identity can, and that is the half that
catches the mistakes people actually make.

Extents therefore stay runtime values, and stage 0 is what checks them. A static
extent comes from the checkpoint metadata. A dynamic extent, such as sequence
length or batch size, is a named symbol that stage 0 carries through the shape
algebra without knowing its value.

Errors split across the two layers. The generated boundary carries these types,
so a caller passing the wrong tensor gets a type error from the ordinary
compiler. A disagreeing extent inside the graph, or between the graph and its
checkpoint, is discharged as compile-time computation in the generator, which is
the ECOOP 2026 formulation.

An extent condition that stage 0 cannot discharge is a compile error. Geas has
no runtime shape check to fall back on, because the MVP has no tier below the
static one. This is the MVP's boundary, stated rather than worked around.

### The Axis Schema Is an Invocation Option

Neither the graph nor the checkpoint says which axis is the batch. An ONNX shape
and a safetensors header both give a tensor's rank and its lengths and nothing
about what they mean. Axis names are a property of the architecture rather than
of either file: two Llama checkpoints of different sizes share their axis names
and differ only in their extents.

So the architecture is named where the graph is named, in the invocation's
options:

```wado
use { Model } from "./model.onnxtext" with {
    generator: {
        module: "wado-lang:geas@0.1",
        inputs: ["./model.safetensors"],
        options: {
            architecture: "llama",
            layout: [{ match: "*.q_proj.weight", axes: ["Hidden", "Hidden"] }],
        },
    },
};
```

The schema names the graph's inputs and its initializers. Every other value in
the graph gets its axes from the operator that produced it, so the names are
written once at the edges and inferred everywhere inside.

Options rather than a second file, because Kiln already rejected a schema a
reader has to go elsewhere to find (§"A manifest-side invocation registry").
Options are typed by the generator's own `Options` struct, so the use site gets
validation and completion that a sidecar document could not have, and they are
canonically encoded into the cache key, so reformatting one does not regenerate.
The probe receives them, which is where `inline_weights` already relies on.

Naming every tensor is not an option at either place. A thirty-layer
transformer has hundreds, so the schema is a name and a set of patterns:
`architecture` selects a table Geas ships, and `layout` holds patterns consulted
in order ahead of it. First match wins, which is what lets one pattern override
a table entry without restating the rest of it.

A tensor that neither reaches is a build error naming it. Geas does not fall
back to positional axes, for the same reason stage 0 does not fall back to a
runtime check.

The tables age, because model formats move. That is safe rather than merely
accepted: a table is read at build time and its answer is baked into the
generated module, so a stale one stops the build with the error above instead of
producing a module that computes the wrong thing.

`architecture` is an option rather than something read from the file.
safetensors has only a free-form `__metadata__` map, which carries no dependable
architecture. A format that does state one, as GGUF's `general.architecture`
does, can have it read and checked against the option.

### The Signature Is the Notation

einx exists because Python cannot say in a type what an operation does to a
shape, so it says it in a string. Wado can say it in a type, and the generator
emits each operator, and the model's boundary, as a generic signature that
carries every part of the notation:

```wado
fn matmul<..Bs, M, K, N>(
    a: &Tensor<f32, [..Bs, M, K]>,
    b: &Tensor<f32, [..Bs, K, N]>,
) -> Tensor<f32, [..Bs, M, N]>
```

A repeated variable is einx's bracket: `K` appears in both operands and not in
the result, which is what contraction means. The unrepeated scalars are the
vectorized axes, the pack is einx's leading ellipsis, and the return type is its
arrow. One signature covers rank 2, 3 and 4, because the pack also matches
empty.

So there is no notation layer. A tagged template could not have been one
anyway: `ReflectTemplate` exposes the hole _types_ and the literal text as a
_value_, with no associated type derived from the literal, and einx's entire
content is in that literal. A tag could only return a tensor whose axes had
been erased, discarding what the type layer just won.

A pack is limited to one per parameter list, so an axis list cannot be written
`[..Pre, K, ..Post]` and a contraction over a middle axis needs an explicit
transpose first. This is a tax rather than a barrier. Trailing-axis contraction
is how transformer code is already written, since it is what BLAS wanted, and
`K^T` is a transpose everyone writes by hand. A rank-2 weight broadcasts across
batch axes by putting the pack on one side only, which is the case that would
otherwise have hurt.

### The Backend Is a Trait

A `Backend` trait, monomorphized at each use, selects where kernels run. The
MVP ships one implementation, on the CPU.

An effect was considered and set aside. Wado's effects lower through stack
switching, whose per-operation cost is unmeasured here, and a tensor dispatch is
a hot path. A trait's cost is known to be zero.

The CPU backend is for correctness and for the seam, not for speed. Wasm SIMD
loads from linear memory and a Wado `List<T>` is a WasmGC array with no address,
so `core:simd` offers no load: a vector is built by `splat`, by tuple coercion,
or by reinterpreting another vector. The pattern that does pay is `core:prng`'s,
where vectors stay in the dataflow and never come from a list, which suits a
tile held across a long computation and little else. The performance story
belongs to the GPU backend.

### The MVP Is Tier 1 Only

Gale's two tiers become three here. This WEP builds the first:

| Tier              | Decided at        | Covers                               |
| ----------------- | ----------------- | ------------------------------------ |
| Static (tier 1)   | build time        | Static shapes, weights, fused blocks |
| Bucketed (tier 2) | first use, cached | Residual sequence and batch extents  |
| Dynamic (tier 3)  | per token         | MoE routing, speculation, early exit |

Tiers 2 and 3 are deliberately absent, not undiscovered.

Tier 2 is a shape-class cache rather than a simulator. Generating a kernel is
expensive where Gale's ATN step is cheap, and the generation must finish before
the dispatch it serves can run. Tier 3 is the genuine analogue of Gale's ATN:
data-dependent control flow that no bucketing covers.

### The Generator Reports Every Fusion Decision

`gale dump` is what makes Gale's escalation auditable, and its absence is why
`torch.compile`'s graph breaks arrive as a mystery. Geas's generator reports,
per operation, what it fused, what it did not, and why.

The MVP has one tier and reports anyway. A declined fusion carries the reason
it was declined, and those reasons are what will route the later tiers.

### What the CPU MVP Cannot Validate

The MVP validates the shape algebra, the generator architecture, and the backend
seam. It does not validate the fusion objective.

On CPU the objective is memory traffic. On WebGPU at batch size 1 it is dispatch
count. They are different objectives, and a fusion policy tuned against the
first is not evidence about the second. The GPU WEP will have to re-derive its
policy from measurement rather than inherit this one.

The CPU arm cannot even reach its own objective's ceiling, for the reason in
"The Backend Is a Trait": no vector load from a WasmGC array. A number this MVP
produces is a correctness result and a floor, never a claim about the design.

## Roadmap

1. The graph reader and the extent algebra. A Gale grammar for the ONNX textual
   format, and static and symbolic extents carried through each operator's
   ONNX signature inside the generator. Axis identity is already settled and
   demonstrated by `example/tensor_axes.wado`, so what is left is the extent
   half. Finished when a two-layer MLP in `.onnxtext` with a mismatched extent
   is a compile error naming both disagreeing extents.
2. The kernels. Each operator lowering to a Wado loop nest, checked against the
   ONNX backend test data for that operator. Finished when every operator the
   MLP uses passes its conformance cases.
3. The checkpoint reader. safetensors in the generator, its header checked
   against the graph. safetensors comes first because its header is already
   JSON, with no quantization to model. Finished when a real checkpoint's
   shapes check against its graph, and a deliberately mismatched one names the
   axis.
4. The backend seam. The `Backend` trait with its CPU implementation. Finished
   when the MLP from step 1 runs through the trait and matches the reference
   within tolerance.
5. The fusion report, following what `gale dump` established. Finished when
   every operation in the step-3 model reports a decision and a reason.
6. End to end. A small real model runs and produces correct output, with a
   `benchmark/` row against onnxruntime's CPU execution provider on the same
   graph. Finished when the row is in `benchmark/README.md`.
7. The StableHLO front end. Finished when the MLP exported from JAX checks and
   runs through the same pipeline as its ONNX form.

## Known gaps

Tier 2, the bucketed JIT. Residual sequence and batch extents need a
shape-class cache populated on first use. Closing it needs a cache key design, a
warmup story, and an answer to generation latency becoming user-visible. Gale's
generator is 1.40x slower than ANTLR4's, which is free at build time and is not
free at first use.

Tier 3, dynamic dispatch. MoE routing, speculative decoding, and early exit are
data-dependent and no bucketing covers them. Closing it needs the escalation
boundary drawn as a decidability question, as Gale's is, rather than as a
heuristic.

The GPU backend. A second `Backend` implementation over `wasi:webgpu`, with the
fusion objective re-derived for dispatch count. This is a WEP of its own.

Quantization. Block formats are parameterized by block size, scale
representation, and rotation, so the type that carries one must be
parameterized the same way rather than named after a format. GGUF as an input
format arrives with this, not before it, and its metadata is a binary key-value
block rather than JSON, so its probe has to parse one to report an extent.

ONNX in its protobuf form. Reading one needs a protobuf parser in Wado and the
tree has none, so a model exported as protobuf is converted to text outside the
build. The external-data requirement above is what the parser would then read
against.

Whole checkpoints are still read. An extent describes a read of the header
alone, but today it saves the hashing rather than the read, so a gigabyte file
is loaded in full on every build. Roadmap step 3 is the first caller that makes
this visible; the Kiln WEP records what closing it takes.

Training. Geas is an inference design. An autograd layer over the same shape
algebra is plausible and unowned.

Contraction over a middle axis. One pack per parameter list means an axis list
cannot be written `[..Pre, K, ..Post]`, so such a contraction costs an explicit
transpose and the data movement it implies. Closing it means a second pack, or
an operation that names its contraction axis some other way.

Whether the backend should be an effect after all. The trait is chosen because
its cost is known to be zero and the effect's is unmeasured. A second backend
makes the measurement possible.
