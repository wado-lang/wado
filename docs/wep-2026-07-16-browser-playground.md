# WEP: Browser Playground on the Wado Site

## Context

The official site (`wado-lang/wado-lang.github.io`) needs a playground page:
a single standalone page, styled like the landing page, with a two-pane
layout — a Monaco-based editor backed by `wado-lsp` on the left, and the
program's stdout/stderr on the right.

This WEP is the follow-up that `wep-2026-04-18-lsp-architecture.md` deferred
("A follow-up WEP will design the JS/TS host and transport for the public
site"). It designs the whole page: the LSP browser host, the compile-and-run
pipeline, the UI, and how the artifacts reach the static site.

### What exists today

- `wado-playground/` — a wasm32-unknown-unknown wrapper exposing
  `wado_alloc` / `wado_compile` / `wado_free` over `compile_with_options` +
  `InMemoryCompilerHost`. The stdlib is embedded (`include_str!`), so a
  single-file program compiles with no host I/O. Built with
  `no-wide-arithmetic` (V8 lacks the wide-arithmetic proposal).
- `wado-playground/web/` — a proof-of-concept page. `playground.js` runs the
  full client-side pipeline: compile → `transpileBytes` (jco, bundled for the
  browser by `build-jco.mjs`) → postprocess → `import()` of a blob module with
  WASI P3 browser shims (`shims/{cli,clocks,random}.js`) → captured
  stdout/stderr. Verified end-to-end by `mise run playground-web-test`.
- `wado-lsp` — one server implementation, two targets. The `wasm32-wasip1`
  build (stdio, Content-Length-framed JSON-RPC) already powers the VS Code
  extension. Capabilities: diagnostics (push), hover, definition, references,
  document highlight, semantic tokens (full), inlay hints.
- The site — static `index.html` + assets, no build step for the landing
  page; blog/docs generated by Sheaf in the deploy workflow. Published on
  GitHub Pages. The `wado` CLI is already consumed from GitHub Releases.

### Constraints

- **GitHub Pages cannot set response headers.** No COOP/COEP, so
  `SharedArrayBuffer` (and `Atomics.wait`-based blocking stdin) is
  unavailable without service-worker hacks.
- **JSPI is already a hard requirement.** Both the transpiled program and
  jco's own bindgen use `WebAssembly.Suspending`; Chrome/Chromium 137+ is the
  supported browser. The design may lean on JSPI freely.
- **The site repo has no Rust toolchain.** Its deploy builds the blog with
  the released `wado` CLI in a few minutes; compiling `wado-compiler` to Wasm
  there would add a 10+-minute Rust build and a toolchain to every site push.
- **The artifacts are large.** Both `wado-playground.wasm` and
  `wado_lsp.wasm` embed the full compiler. Loading must be lazy and
  cache-friendly.
- The landing page currently loads zero external resources; the playground
  should stay self-hosted (no CDN).

## Decision

### Ownership split: runtime in `wado`, page in the site repo

Everything that must stay in lockstep with the compiler ships from this
repository as one versioned release asset, `wado-playground-web.tar.gz`:

```
wado-playground.wasm       compile: source → CM component (existing build)
wado-lsp.wasm              wasm32-wasip1 LSP server (same artifact as VS Code)
playground.js              compile/transpile/run pipeline (existing, DOM-free)
runner-worker.js           Worker entry wrapping playground.js
lsp-worker.js              Worker entry: WASI p1 shim + wado-lsp.wasm
lsp-client.js              JSON-RPC framing + Monaco provider adapter
monarch.js                 base Monarch grammar for `wado`
shims/                     WASI P3 browser shims (existing)
vendor/                    jco browser bundle + core wasms + postprocess (existing)
monaco/                    pinned monaco-editor min build (vendored from npm)
manifest.json              { "version": "<tag>" } for cache busting
```

The site repo owns the page shell: `playground/index.html` (markup, styling,
UX) plus a small `playground/app.js` that wires the tarball's two APIs
(`lsp-client.js`, `runner-worker.js`) to the DOM. The tarball's JS surface is
a stable contract; the page never reaches into pipeline internals.

Rationale: the shims, the jco bundle, and the LSP wire behavior are coupled
to compiler and jco versions — they belong here, built and tested by this
repo's CI. Look and feel belongs to the site. This mirrors how the site
already consumes the `wado` CLI from Releases.

### LSP browser host: wasip1 module in a Worker, JSPI stdin

`wado_lsp.wasm` (the exact `wasm32-wasip1` artifact the VS Code extension
bundles) runs in a dedicated Web Worker behind a minimal handwritten WASI p1
shim:

- `fd_read` on stdin is a `WebAssembly.Suspending` import that awaits the
  next inbound message. JSPI suspends through the server's blocking read
  loop, so the unmodified stdio binary becomes event-driven. This is why
  neither `SharedArrayBuffer` nor an Asyncify build is needed — and JSPI is
  already required by the run pipeline.
- `fd_write` on stdout feeds a Content-Length frame parser; each complete
  JSON-RPC message is `postMessage`d to the page. stderr goes to
  `console.warn`.
- `clock_time_get`, `random_get`, `environ_*`/`args_*`, `fd_fdstat_get`,
  `proc_exit` get trivial implementations; `path_open` returns `ENOENT`.
  The stdlib (`core:` / `wasi:`) is embedded in the compiler, and the
  playground is single-file, so the `FilesystemCompilerHost` rooted at `.`
  never needs a real filesystem.

`lsp-client.js` (main thread) speaks LSP over the worker port: `initialize`,
`textDocument/didOpen` for `file:///playground.wado`, full-text `didChange`
debounced ~200 ms, and maps responses onto Monaco:

| LSP                                | Monaco                                   |
| ---------------------------------- | ---------------------------------------- |
| `publishDiagnostics` (push)        | `setModelMarkers`                        |
| `textDocument/hover`               | `registerHoverProvider`                  |
| `textDocument/definition`          | `registerDefinitionProvider`             |
| `textDocument/references`          | `registerReferenceProvider`              |
| `textDocument/documentHighlight`   | `registerDocumentHighlightProvider`      |
| `textDocument/semanticTokens/full` | `registerDocumentSemanticTokensProvider` |
| `textDocument/inlayHint`           | `registerInlayHintsProvider`             |

`monaco-languageclient` is rejected: it drags in `vscode-languageclient` plus
VS Code API shims and a bundler, for seven provider mappings that are ~200
lines by hand. The hand-rolled client also keeps the tarball
bundler-free, matching the site's no-build ethos.

Highlighting is layered: `monarch.js` gives instant keyword/string/comment
coloring while the LSP warms up, then semantic tokens refine it. The Monarch
grammar starts handwritten and minimal; generating it from
`wado-compiler/src/syntax.rs` (like the TextMate grammar) is a follow-up.

### Run pipeline: compile → jco → run, in a terminable Worker

The existing `playground.js` pipeline is reused unchanged, but moved off the
main thread into `runner-worker.js`. It is DOM-free already (blob URLs,
`fetch`, dynamic `import()` all work in workers); `globalThis._wadoWrite`
becomes a `postMessage` relay, so stdout/stderr stream into the output pane
incrementally rather than arriving as one blob at exit.

Running in a worker buys two things: the compile (CPU-heavy, in-Wasm) never
janks the editor, and **Stop** is `worker.terminate()` + respawn — the only
way to kill a runaway program, since a blob module on the main thread cannot
be unloaded.

Messages: `{kind: "status", phase: "compiling"|"transpiling"|"running"}`,
`{kind: "stdout"|"stderr", text}`, `{kind: "done", ms}`,
`{kind: "error", text}` (compile diagnostics arrive here and render
stderr-styled).

### The page

`playground/index.html`, published at `/playground/`. Same idiom as the
landing page: inline CSS reusing the palette (`--paper`, `--ink`, `--rule`,
`--code-bg`, `--accent`), the serif body stack for chrome, JetBrains Mono
stack for editor and output, the standard `.topnav` (with a Playground link
added to the landing page nav too).

Unlike the landing page, the main area is full-width (the 720 px column is
too narrow for two panes):

```
┌ topnav ─────────────────────────────────────────────┐
├ toolbar: [Run ⌘⏎] [Stop] · status (“compiled in 480 ms”) ┤
├──────────────────────────┬───────────────────────────┤
│ Monaco editor            │ output                    │
│ (wado, wado-paper theme) │ stdout: ink               │
│                          │ stderr/diagnostics: accent│
├──────────────────────────┴───────────────────────────┤
└ footer (seal · MIT · repo link) ──────────────────────┘
```

- Panes are `flex` 55/45, filling the viewport below the toolbar; below
  ~800 px they stack vertically (editor above output).
- The Monaco theme `wado-paper` matches the site's code blocks:
  `--code-bg` background, keywords in the vermillion accent, strings in
  `#2f5a2f`, comments in `#6b665b` italic — the semantic-token legend from
  `wado-lsp/src/semantic_tokens.rs` maps onto these few colors plus neutrals.
- The editor preloads the landing page's hello-world. Run is the toolbar
  button or Ctrl/Cmd+Enter.
- stdout and stderr interleave in the output pane in emission order; stderr
  and compile diagnostics use the accent color. The status line shows phase
  and timing.
- Feature detection at load: if `WebAssembly.Suspending` is missing, a
  banner says the playground needs a JSPI-capable browser (Chrome/Chromium
  137+); the editor stays usable with Monarch highlighting, Run and the LSP
  stay disabled.

### Loading strategy

Page load fetches Monaco and starts the LSP worker immediately (diagnostics
are the first thing a visitor sees). `runner-worker.js` and its assets
(`wado-playground.wasm`, the jco bundle and its core wasms) are fetched on
the first Run, prefetched in the background once the LSP is ready. All asset
URLs carry `?v=<manifest version>` so GitHub Pages' caching never serves a
stale wasm against new JS.

### CI and deployment

- **This repo**: the release workflow gains a `playground-web` job — run
  `wado-playground/web/build.sh`, build `wado-lsp` for `wasm32-wasip1`,
  `npm ci` a pinned `monaco-editor` and stage `min/vs`, write
  `manifest.json`, tar, attest, and upload `wado-playground-web.tar.gz`
  alongside the CLI archives. `mise run playground-web-test` (extended to
  cover an LSP hover round-trip in the browser) gates it.
- **Site repo**: a `fetch-playground` mise task downloads and unpacks the
  latest release asset into `.tmp/playground/` (gitignored), same
  Releases-based pattern as the `wado` CLI tool. `deploy.yml` copies the
  committed `playground/` page plus the unpacked assets into
  `dist/playground/`. Local dev: `mise run fetch-playground && mise run
  serve`.
- The site's `deploy.yml` already accepts `repository_dispatch`; a follow-up
  adds a dispatch step to this repo's release workflow so a Wado release
  redeploys the site with the new playground.

### Considered alternatives

- **Blocking stdin via `SharedArrayBuffer` + `Atomics.wait`** (how
  `@vscode/wasm-wasi` hosts the same binary). Rejected: needs COOP/COEP,
  which GitHub Pages cannot set; the `coi-serviceworker` workaround is
  fragile (first-load reload, broken deep links). JSPI costs nothing extra
  here.
- **`monaco-languageclient`**. Rejected above: heavy dependency graph and a
  mandatory bundler for a small, stable provider surface.
- **One wasm artifact instead of two** — teach `wado-lsp` a custom
  `wado/compile` request and drop `wado-playground.wasm`, halving the
  download. Attractive, but it couples the LSP wire protocol to the
  playground and both artifacts already exist and are tested today. Deferred
  to a follow-up once real payload sizes are measured.
- **Building the wasm in the site's deploy workflow.** Rejected: adds the
  Rust toolchain and a long compile to every site push, and loses the
  provenance/attestation story the release pipeline already has.
- **Running the transpiled program on the main thread** (the current PoC).
  Rejected for the product page: no Stop, and compilation janks the editor.

## Scope

In scope (v1): the page, the two workers, the LSP client with the seven
capabilities above, streaming output with Stop, the release asset, and the
site deploy integration.

Out of scope, listed for later: code sharing via URL hash, an examples
dropdown, `wado format` on save, a WAT/component-size inspector pane, a
draggable pane splitter, generating the Monarch grammar from `syntax.rs`,
the single-artifact `wado/compile` unification, and auto-redeploy dispatch
on release.

## Test plan

- `mise run playground-web-test` grows two browser assertions: an LSP
  round-trip (didOpen → publishDiagnostics on a program with a type error;
  hover over `println` returns a signature) and a runner-worker run of
  hello-world asserting streamed stdout, both against the exact staged
  tarball layout.
- The site page is smoke-tested with the repo's Playwright screenshot recipe
  during development; the deploy workflow fails if the release asset is
  missing or its `manifest.json` is unreadable.
