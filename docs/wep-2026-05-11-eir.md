# WEP: Explicit IR (EIR) Layer

## Context

The compiler pipeline from `lower` to `wir_build` runs entirely on `FlatPackage` with TIR-shaped function bodies:

```
... → link → monomorphize → erase → lower → optimize → wir_build → ...
                                    └─── FlatPackage (TIR bodies) ───┘
```

`lower/` is a series of `FlatPackage → FlatPackage` transformations (`wide_int`, `pattern`, `globals`, `boxing`, `closure`, `string`, `value_copy`). The output is structurally the same type as the input.

This produces three problems that compound over time:

- Optimize and `wir_build` see the union of pre-lower and post-lower TIR variants. Several passes carry match arms for variants that `lower` has, in practice, eliminated. These arms are required for exhaustiveness but never taken at runtime.
- The "lower has run" precondition is implicit. A newly written pass can rely on a pre-lower shape; the type system does not catch it.
- Concepts introduced by lower (boxing, closure functorization, pattern → switch) are expressed by overloading existing TIR variants. Intent is recoverable only by tracing the lowering source code.

A second pressure reinforces the first. Removing the AST-level `desugar` phase (see [LSP architecture](./wep-2026-04-18-lsp-architecture.md)) would push additional variants into TIR. Without a downstream type boundary, every optimize pass would grow further. A boundary at `lower` contains the blast radius.

## Decision

Introduce **EIR (Explicit IR)** — a separately-typed body IR. `lower/`'s output type changes from `FlatPackage` to `EirPackage`. `optimize/` and `wir_build/` consume `EirPackage`.

### What EIR Is

EIR is structurally derived from TIR. At the moment EIR lands, its expression, statement, type, and container shapes are identical to their TIR counterparts. They are distinct Rust types — separate enums, separate visitor traits — but they represent the same data.

The content of this Decision is the type boundary, not a shape redesign:

- TIR is what flows from `annotate` through `synthesis` / `effect_check` / `link` / `monomorphize` / `erase` into `lower`'s input.
- EIR is what flows out of `lower` through `optimize` into `wir_build`.
- A function signature naming one of these never names the other.

### What EIR Is Not

- Not a redesign. This WEP introduces no new node kinds, removes no variants, and changes no semantic behaviour. Wasm output is bit-identical before and after.
- Not a CFG or SSA representation. EIR keeps TIR's tree-structured shape. Wado has no borrow check, and Wasm has structured control flow; the tree shape is appropriate.
- Not the home for sugar removal. Sugar elimination is `desugar`'s responsibility today, on AST. If `desugar` is later removed, sugar elimination moves to `lower_tir` (AST → TIR). Neither path produces sugar that flows into EIR.
- Not a replacement for FlatPackage. FlatPackage continues to be the pre-lower container; EirPackage is the post-lower container. Both exist after this WEP.

### Why "Explicit"

The name signals direction. Lower today encodes its decisions (boxing as struct construction, closures as struct construction, patterns as switch over discriminants) by reusing pre-existing TIR variants. The eventual goal is to introduce named nodes that surface those decisions at the type level — an `Alloc` distinct from `StructLiteralExpr`, a `Closure` distinct from a generic struct literal, a `Switch + PayloadExtract` distinct from rich `MatchExpr`. EIR's existence is the prerequisite for that work; this WEP establishes the boundary. Future WEPs may add the explicit nodes.

## Implementation

### Source Files

| File             | Description                                                                                              |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| `eir.rs`         | EIR data structures: `EirExpr`, `EirStmt`, `EirPattern`, `EirPackage`. Initially direct copies of TIR's. |
| `eir_visitor.rs` | EIR visitor trait. Initially a direct copy of `tir_visitor.rs`.                                          |
| `eir_unparse.rs` | EIR → pseudo-Wado renderer for `wado dump --eir`.                                                        |

### Container

`EirPackage` mirrors `FlatPackage`: function table, type table reference, global table, exports, imports. Field shapes match initially.

### Data Sharing With TIR

EIR reuses without copying:

- `TypeTable` (post-erase): types are interned globally, not per IR. EirPackage holds a reference in the same shape FlatPackage does.
- `SymbolKey`, `FunctionId`, `GlobalId`, name interners.
- `Literal`: value representation is independent of expression shape.

EIR owns its own:

- Expression / statement / pattern enums and their inline metadata.
- Visitor trait.

This follows the convention `WirPackage` already uses: `WirTypeId` borrows TIR-level type identity, while `WirInstr` is a fresh enum.

### Lower Phase Role

`lower/` continues to perform the same semantic work. Only its output type changes:

```rust
// Before
fn lower(package: FlatPackage) -> FlatPackage

// After
fn lower(package: FlatPackage) -> EirPackage
```

Because EIR is initially structurally identical to TIR, the cross-type conversion at lower's exit is mechanical: field-for-field reconstruction. The internal sub-passes (`wide_int`, `pattern`, `globals`, `boxing`, `closure`, `string`, `value_copy`) keep their current implementations.

### Inspection

`wado dump --eir` renders `EirPackage` as pseudo-Wado, paralleling `--tir` and `--wir`.

## Migration Plan

EIR starts structurally identical to TIR. No parallel pipeline (strangler fig) is required; the change is a sequence of in-place renames.

### Phase 1: Add EIR types

- [ ] Create `eir.rs`, `eir_visitor.rs`, `eir_unparse.rs` as renamed copies of their TIR counterparts.
- [ ] Create `EirPackage` as a renamed copy of `FlatPackage`.
- [ ] Wire `wado dump --eir`.

No pipeline change yet. E2E tests are unaffected.

### Phase 2: Lower returns EirPackage

- [ ] Add a `FlatPackage → EirPackage` conversion at the exit of `lower/`.
- [ ] Change `lower/`'s public signature.
- [ ] Add a temporary `EirPackage → FlatPackage` adapter so downstream consumers continue to work unchanged.

### Phase 3: Migrate `optimize/`

- [ ] Rename `TirExpr`/`TirStmt`/`FlatPackage` references inside `optimize/` to their EIR counterparts, pass by pass.
- [ ] Each pass migration is mechanical — same logic, renamed types.

### Phase 4: Migrate `wir_build/`

- [ ] Change `wir_build/build_wir_package`'s input type to `EirPackage`.
- [ ] Rename references inside `wir_build/`.

### Phase 5: Remove the temporary adapter

- [ ] Delete the `EirPackage → FlatPackage` adapter added in Phase 2.
- [ ] Confirm E2E tests pass with the full EIR pipeline.

Subsequent work (variant trimming, explicit-node introduction, removing the AST-level `desugar` phase) is out of scope for this WEP. Each lands as its own follow-up.

## Consequences

### Benefits

- Type boundary at `lower`. The "lower has run" precondition is enforced statically.
- Risk concentrates on `lower`. Optimize and `wir_build` migrations are mechanical renames; the semantically interesting work stays in the smallest of the three phases.
- Enables future variant trimming. With two distinct enums, variants only meaningful pre-lower can leave EIR, and variants only meaningful post-lower can leave TIR. Each trim is a small PR enforced by the type system.
- Enables explicit-node introduction. Adding `Alloc`, `Closure`, `Switch`, `PayloadExtract` etc. on the EIR side becomes safe because EIR owns its enum.
- Enables removal of the AST-level `desugar` phase. Adding variants to TIR (the consequence of moving sugar elimination into `lower_tir`) does not propagate into optimize.

### Trade-offs

- Code duplication on landing. EIR's expression / statement / visitor / unparse files start as copies of TIR's. The duplication is intentional and is paid down in subsequent WEPs as the two diverge. Copying is mechanical and reviewable in one sitting.
- A short window during the transition where both `FlatPackage` and `EirPackage` flow through downstream code. The Phase 2 adapter absorbs this; Phase 5 removes it.
- One more `wado dump` mode to maintain.
